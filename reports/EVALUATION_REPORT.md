### 2.2. Инженерные решения

- **Сегментация v2** (`grounding.segment_claims`). Прежнее разбиение резало «SP 800-53 Rev. 5», «No. 1», «e.g.» и «LIKE ... INCLUDING» на обрывки и считало «;» границей утверждения; обрывок до маркера [S#] оставался без цитаты и блокировался без вызова NLI. Теперь сокращения и номера защищены, «;» не делит утверждение, хвост ссылок вида «[S1], [S2]» остаётся с предложением.
- **Наследование ссылки** (`grounding.cited_claims`). Предложение без [S#] получает ссылку следующего предложения того же абзаца, затем предыдущего, затем ближайшую в ответе; опубликованное унаследованное утверждение получает маркер явно. Неверный маркер ([S0], [S 1]) не наследуется: такое утверждение отклоняется, как и раньше.
- **Очистка посылки и оконная проверка** (`NLIFactVerifier._evidence`). Длинный чанк смешивает нужное предложение с соседними строками таблиц и условиями, и mDeBERTa выдаёт ложное противоречие на дословно подтверждённом утверждении. Посылка очищается от служебного заголовка и HTML, затем одним пакетом оцениваются чанк и все окна из 1-2 предложений. Окно поддерживает утверждение при строгих порогах; окно, содержащее все числа и идентификаторы утверждения, - при мягких; дословный фрагмент синтаксиса (ABNF, флаги) - при отсутствии сильного противоречия.
- **Якоря** (`grounding.claim_anchors`). Число, код, флаг или идентификатор утверждения обязан встречаться в процитированном чанке (с учётом границ числа: «20» не находится в «2020»); иначе утверждение не может быть подтверждено никакой вероятностью NLI. Обозначения документов («RFC 9110», «SP 800-63B-4») якорями не считаются.
- **Поддержка важнее шума** (`nli_aggregation=support_first`). Прежнее правило блокировало утверждение, если любой из процитированных источников давал P(con) ≥ 0.2, даже когда другой источник его дословно подтверждал. Теперь достаточно одного подтверждающего источника; другой блокирует только явным противоречием (P(con) ≥ 0.9).
- **Оговорки и исправления предпосылки** (`abstention_guard`). Фраза «документ не содержит сведений о ...» не подтверждается NLI по построению; раньше фильтр удалял её и публиковал оставшийся смежный факт, внося галлюцинацию. Теперь такие фразы публикуются как оговорка и не считаются заблокированными, ответ только из оговорок становится каноническим отказом, а исправление предпосылки («Нет, ...») не публикуется без подтверждённого обоснования.
- **NLI в float16 пакетами.** В bf16 вероятности одной и той же пары заметно различаются между пакетом с паддингом и одиночным вызовом; float16 совпадает с float32 по метрикам при той же памяти, поэтому окна оцениваются пакетами в float16.
- **Поиск.** Итоговый балл = alpha · RRF + (1 - alpha) · rerank; при alpha 0.2 порядок задаёт кросс-энкодер, RRF (k = 30) разводит близкие баллы; реранкер оценивает 40 кандидатов вместо 60 (alpha 0.8, k = 60 в базовом прогоне). Вес BM25 умножается на долю терминов запроса, найденных в словаре индекса: русский вопрос к англоязычному RFC почти не даёт лексического сигнала и не должен вытеснять dense-кандидатов.
- **Промпт.** Добавлены требования: каждое предложение заканчивается ссылкой, составной вопрос - отдельное предложение на каждую часть, числа, коды, идентификаторы и правила ABNF переносятся дословно. Дословный перенос делает утверждение проверяемым NLI и якорями; цена - больше англоязычных цитат в русском ответе; черновик чаще отвечает там, где ответа нет или предпосылка ложна (галлюцинации Vanilla RAG 2 из 93 в базовом прогоне и 10 из 93 в этом, guard вкл.; в пилотах 2.3 рост появляется вместе с новым промптом), и удерживать их приходится фильтру.
- **Повторная генерация** (`generation_repair_attempts = 1`). Если NLI отклонил ответ, LLM получает отклонённые утверждения и сужает ответ до подтверждаемых фактов. Vanilla RAG в отчёте - всегда первый черновик, повтор относится к FactRAG-NLI. В этом прогоне (guard вкл.) повтор понадобился в 35 кейсах: опубликован ответ в 5, корректный исход в 18 (включая верные отказы), галлюцинаций после повтора 0.

### 2.4. Что не сработало

- Окна из трёх предложений вместо двух не добавили подтверждённых утверждений на dev.
- Замена обозначений документов в гипотезе («RFC 9110» → «документ») снижала перехват искажений: часть проб проверяет именно приписывание факта документу.
- Проверка утверждения без ссылки против всех источников ответа и изменение доли заблокированных утверждений, при которой ответ заменяется отказом (0.5), исход не меняли.
- Правило «отказ, если удалено первое утверждение с отрицанием» увеличивало ложные отказы; оставлено только правило для исправления предпосылки без обоснования.
- Повышение точности NLI (bf16 → float16/float32) само по себе ошибки не исправляет: это видно по второй строке абляции.

### 3.3. Режимы и метрики

- **Поиск** (без LLM): для каждого вопроса одним вызовом получены пять ранжирований: dense (BGE-M3, Qdrant), sparse (BM25), гибрид RRF, RRF с реранкингом до порога и боевой список после порога релевантности 0.05. Recall@K считается по единицам эталонного контекста (единица найдена, если в топ-K есть любой её чанк), MRR@10 и nDCG@K с бинарной релевантностью.
- **NLI** (без LLM): боевая функция `NLIFactVerifier._claim` на эталонной посылке и гипотезе. Отдельно оценены argmax трёх классов (матрица ошибок, P/R/F1) и решение боевого правила: *Hallucination Catch Rate* (доля проб Contradiction/Neutral, не получивших VERIFIED) и *False Rejection Rate* (доля проб Entailment, не получивших VERIFIED).
- **Сквозной прогон**: полный конвейер на 220 вопросах. *Vanilla RAG* = первый черновик LLM до NLI-фильтра (`raw_answer`), *FactRAG-NLI* = опубликованный ответ; оба получены из одного вызова конвейера (повторная генерация после отказа NLI относится к FactRAG-NLI), поэтому сравнение парное. Отказ = канонический текст отказа; воздержание = отказ или явная фраза об отсутствии сведений. Корректность: для отвечаемых вопросов все ключевые факты (`answer_must_contain`) присутствуют; для вопросов без ответа воздержание; для adversarial воздержание или верный факт-исправление. Галлюцинация определена только там, где истина зафиксирована датасетом: ответ на вопрос без ответа или adversarial-ответ без верного факта.

## 7. Ограничения

- *Vanilla RAG* в этом отчёте - черновик той же LLM с тем же промптом (включая premise guard в прод-профиле) и тем же порогом релевантности, а не внешняя базовая система; сравнение изолирует вклад NLI-фильтра.
- Все документы корпуса англоязычные. При `RAG_GENERATION_LANGUAGE=ru` 103 из 194 черновиков написаны преимущественно кириллицей (на английские вопросы: 20 из 101), поэтому NLI в основном сравнивает русскую гипотезу с английской посылкой; на контрольных парах доля ложной отбраковки для EN- и RU-гипотез приведена в разделе 4.2.
- Разметка датасета подготовлена ИИ; механические проверки (дословные цитаты, отсутствие терминов в корпусе, дедупликация) не заменяют экспертную проверку смысла.
- Корректность ответа оценивается по ключевым фактам (`answer_must_contain`), а не экспертом: ответ с верным числом, но лишним неподтверждённым утверждением считается верным; правильный ответ другими словами может быть засчитан как неверный.
- Галлюцинации на уровне кейса определены для вопросов без ответа и adversarial; лишние неподтверждённые утверждения в ответах на отвечаемые вопросы этой метрикой не учитываются (их видно в статусах утверждений).
- Один прогон на профиль при temperature 0 и фиксированном seed; разброс между прогонами не измерялся.
- Корпус открытый (RFC, NIST, PostgreSQL, PEP), вопросы RU/EN; ГОСТ/СП и другие русскоязычные нормативные документы не измерялись.
- Пороги верификатора подобраны на dev-половине (110-111 кейсов); test-половина того же размера даёт оценку переноса, но не заменяет независимый датасет.
- NLI проверяет выводимость утверждения из источника, а не то, отвечает ли оно на вопрос: верный по источнику смежный факт проходит фильтр. Утверждение, добавляющее субъект, которого нет в окне («A QUIC client ...», «RFC 9110 specifies ...»), mDeBERTa часто оценивает как Neutral, хотя чанк взят из этого документа; служебный заголовок чанка содержит хэш документа, а не название, поэтому дать модели этот контекст без переиндексации нельзя.
- `replay` повторяет только первую попытку генерации и требует локальных логов `full/` исходного прогона (не хранятся в git).

## 8. Воспроизведение

```powershell
python scripts/build_eval_dataset_v3.py            # пересобрать и проверить датасет
.\tools\llama\llama-server.exe -m .\models\llm\Qwen2.5-14B-Instruct-Q4_K_M.gguf -ngl 25 -c 4096 -b 128 -ub 64 -np 1 --cache-ram 0 --port 8080 --host 127.0.0.1
python evaluate_suite.py --run-dir reports/runs/20261026T2139Z_v3 retrieval
python evaluate_suite.py --run-dir reports/runs/20261026T2139Z_v3 nli
python evaluate_suite.py --run-dir reports/runs/20261026T2139Z_v3 e2e --profile guard_on
python evaluate_suite.py --run-dir reports/runs/20261026T2139Z_v3 e2e --profile guard_off
python evaluate_suite.py --run-dir reports/runs/20261026T2139Z_v3 replay --source reports/runs/20261026T1410Z_v3
python scripts/render_report.py reports/runs/20261026T2139Z_v3 --baseline reports/runs/20261026T1410Z_v3
```

`replay` не вызывает LLM и поиск: он заново проверяет сохранённые черновики (`full/e2e_<profile>.jsonl`, не хранятся в git) и NLI-пробы и поэтому выполняется за минуты; им удобно проверять любое изменение верификатора до полного прогона.

Режимы выполняются последовательно: встроенный Qdrant допускает одного владельца индекса. Индекс `.artifacts/eval-v3-index` строится при первом запуске и проверяется при каждом следующем (число чанков и наличие всех эталонных `chunk_id`).
