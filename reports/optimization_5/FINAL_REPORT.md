# optimization_5: итоговый отчёт

Ветка `factrag-opt5`.

**Итог:**

## 1. Причина дефекта

Подробно - `PARSER_REPORT.md`, раздел 1. Кратко: в 1929Z на 27 вопросах v3 с ответом в таблице
Recall@10 был 0.52 и верных 16 из 27 (на тексте - 0.98 и 132 из 145). Причины - в разборе, на
всех трёх путях:

| Путь | Дефект |
|---|---|
| все | `_CAPTION` знал только «Таблица N»: 0 из 919 табличных чанков с подписью |
| все | `_NUMBERED_HEADING` делал заголовком любую строку с числом в начале: 2024 из 5358 чанков (38%) под ложным разделом, RFC нарезаны на обрывки (медиана чанка RFC 9110 - 236 символов) |
| текст (RFC) | рамки сетчатых таблиц обрывали таблицу: строка = отдельная «таблица» без шапки, 245 чанков из одной шапки; многострочные ячейки разрывались |
| PDF (SP 800-53) | пустые столбцы раскладки (`Col1\|ID\|Col3\|...`); заголовки контролей не распознавались |
| HTML (SP 800-63B, PostgreSQL) | конвертер терял текст заголовков и связь шапки со значениями в таблицах |

- **`run_benchmark.sh`:** этапы v3 при v2 используют свой индекс `.artifacts/eval-v3-index-parser-v2`, индекс v1 не тронут.
- **`run_experiments.sh` `PLAN=opt5`:** E1, D0, G2, G2 + E1 против прогона v2. Планы optimization_4 по-прежнему работают с v1 и 1310Z.

## 8. Выводы и рекомендации

1. **Дефект разбора реальный и исправлен.** Он затрагивал любой английский документ с таблицами и нумерацией, а не отдельные вопросы. Структура корпуса v3 теперь правильная: 0 ложных разделов, таблицы целые, с шапкой и подписью. Поиск по таблицам вырос вдвое (hit@10 0.37 -> 0.70), русские документы не изменились.
2. **Прирост верных ответов есть, но небольшой** (+5 по оценщику), и **статистически не значим**. Направление совпадает с прогнозом по поиску, но на 1307 вопросах (погрешность около 10 вопросов) это не доказано.
3. **Разбор v2 включён** в профиль 3090 по умолчанию.
   - Выполнены критерии: прирост на dev, меньше галлюцинаций и ложных отказов, каждая потеря разобрана.
   - Буквально не выполнен один: по оценщику появилась одна новая галлюцинация (UNA-028). Её содержание - дословная фраза источника. Если считать это неприемлемым, `PARSER=v1` возвращает прежнее поведение без других изменений.
4. **G2 и E1 отклонены** по критерию 4. Оба безопасны и могут вернуться, если на новых данных дадут прирост на dev.
5. **optimization_5 можно считать завершённой.** Дальнейшая настройка под этот набор вопросов не рекомендуется: test уже несколько раз использован для итоговых оценок.

## 9. Оставшиеся ограничения

- **Проверка рассчитана на текст, а модель теперь чаще опирается на таблицы.** Снятых утверждений со ссылкой на таблицу 6 -> 15 (TC-021, TC-025). Возможное исправление: посылка NLI по строке таблицы (шапка + строка) и якоря без разделителей ячеек. Это изменение защитного слоя, отдельное решение.
- **Межъязыковые табличные вопросы** (русский вопрос, английская таблица: TC-009, TC-018, TC-026 частично) остаются слабым местом поиска.
- **Заголовки контролей** распознаются по форме каталогов контролей SP 800-53. Многоуровневые шапки таблиц PDF не восстанавливаются: PyMuPDF их не размечает. Единственный PDF корпуса - SP 800-53.
- **Оценщик:** промахи на верных ответах (MH-028 и прежние XQuAD) и чувствительность к формулировке на неотвечаемых (UNA-008 / UNA-028). Отдельный список проверенных эквивалентов по-прежнему не заведён, это решение за автором датасета.
- **Офлайн-повтор** (`research.opt3.replay`) не моделирует перевод вопроса G3: на прогонах с G3 повтор B00 расходится на вопросах с переводом (5 в 1222Z).
