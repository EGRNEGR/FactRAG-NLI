# optimization_5: разбор английских таблиц и заголовков (parser v2)

Базовая линия - полный прогон `20261103T1929Z_rtx3090_main` (код 0a70b04, 1188 / 1307).
На 27 отвечаемых вопросах v3, где ответ лежит в таблице, Recall@10 был 0.52 и верных ответов
16 из 27; на 145 текстовых - 0.98 и 132 из 145 (`reports/optimization_4/FULL_RUN_1929Z.md`).
Этот отчёт - этапы 1-2 задачи: причина дефекта, исправление, проверки, сравнение поиска.

## 1. Причина дефекта

Корпус v3: один PDF (SP 800-53), пять RFC в виде текста, SP 800-63B и две страницы PostgreSQL в
виде HTML, сконвертированного в Markdown. Дефекты на всех трёх путях разбора:

| Где | Дефект | Следствие |
|---|---|---|
| `_CAPTION` (`document_parser.py`) | знает только «Таблица N» | 0 из 919 табличных чанков с подписью; «Table 1 of SP 800-53» не находит свою таблицу |
| `_parse_lines`, RFC | граница таблицы `+====+` / `+----+` не содержит «\|» и обрывает таблицу | каждая строка таблицы RFC - отдельная «таблица» без шапки: таблица QUIC разбита на 5 чанков по 184 символа, 245 табличных чанков из одной шапки |
| `_parse_lines`, RFC | ячейка, перенесённая на несколько строк, становится несколькими строками таблицы | «The randomly or» / «pseudorandomly generated» - разные строки |
| `_parse_pymupdf` | `to_markdown` оставляет пустые столбцы раскладки | Table 1 SP 800-53 записана как 12 столбцов `Col1\|ID\|Col3\|...`, 8 пустые |
| `_NUMBERED_HEADING` | заголовок - любая строка, начинающаяся с числа | 2024 из 5358 чанков (38%) под ложным разделом: «15 minutes inactivity» (ячейка таблицы, 303 чанка), «24 hours when sent...», «48 through 51 of the UUID).», пункты списков «2 Procedures to facilitate...», адрес «100 Bureau Drive», строки оглавления, линейка битов «0 1 2 3 ...» |
| `_NUMBERED_HEADING` + чанкер | чанк обрывается на каждой смене раздела | RFC нарезаны на обрывки: медиана чанка RFC 9110 236 символов |
| `TextExtractor` (HTML -> Markdown) | текст заголовка на строке после `#`, каждая ячейка таблицы - своя строка | у SP 800-63B ни одного заголовка, связь шапки и значения в таблицах потеряна |
| SP 800-53, PDF | заголовки контролей («AC-7» над «UNSUCCESSFUL LOGON ATTEMPTS») и усилений не распознаются | 113 чанков «3.1 ACCESS CONTROL» не знают, к какому контролю относятся; идентификатор «AC-7» уходит в соседний чанк |

## 2. Исправление

Локальные изменения в существующем коде, без переписывания разбора. Переключатель
`settings.parser_version` (`RAG_PARSER_VERSION`, на 3090 `PARSER=v2`): `v1` - по умолчанию,
вывод побайтно прежний; `v2` - исправленный разбор.

- **Подписи:** «Table 4: ...», «TABLE 1: ...», «Table 2. ...». Разделитель «:» или «.» обязателен: проза «Table 2 lists ...» не подпись. RFC ставит подпись после таблицы - она относится к таблице перед ней. Подпись повторяется в каждом чанке таблицы, как уже повторялась шапка. Русская «Таблица N» - как в v1.
- **Сетчатые таблицы RFC:** границы `+===+` и `+---+` входят в таблицу; шапка - строки до границы с «=»; многострочные ячейки склеиваются («time-» + «based» = «time-based»). Битовые диаграммы (`+-+-+`, сегменты из одного «-») не затрагиваются.
- **Таблицы PDF:** собираются из ячеек; столбцы, пустые во всех строках, удаляются; ячейка шапки, покрытая объединением (None), берёт текст ячейки слева.
- **Заголовки:** нумерованная строка - заголовок, только если читается как заголовок.
  - Многоуровневый номер («4.2», «15.4.3.»): с заглавной буквы или цифры («302 Found»), без точки, запятой, двоеточия или «;» в конце.
  - Одноуровневый («2», «2.», «J.») дополнительно:
    - номер не больше 99;
    - не больше 12 слов;
    - без «[» и непарных скобок;
    - следующая строка не продолжает фразу со строчной буквы;
    - у буквенного номера нет запятой (список авторов).
  - Не заголовки: строка с отступом (пункт списка RFC), строка оглавления с точками-заполнителями, `# ...` с отступом (комментарий в коде RFC).
  - Русские заголовки ГОСТ («1 Область применения», «4.2 Давление») - заголовки, как и раньше.
- **Заголовки контролей SP 800-53:** «AC-7» над заглавной строкой - контроль, «(4) TITLE | TITLE» - усиление; вложены под нумерованный раздел («3.1 ACCESS CONTROL > AC-7 UNSUCCESSFUL LOGON ATTEMPTS > (4) ...»). Строка сводной таблицы в обычном регистре («AC-9 / Previous Logon Notification») - не заголовок.
- **HTML:** новый `MarkdownExtractor` в `scripts/download_quality_corpus.py` пишет заголовок одной строкой («## Title») и таблицу как Markdown-таблицу:
  - colspan повторяет ячейку вправо, rowspan вниз;
  - строки шапки сливаются в одну («Secret / Type»);
  - вложенная таблица становится текстом ячейки.

  Результат - в `data/test_docs/derived_v2/`. Старый `TextExtractor` и `derived/` не тронуты.

Сопутствующее:
- **`evaluate_suite.build_settings`:** версия разбора берётся из датасета (`chunking.parser_version`, без поля - v1), поэтому датасет v1 нельзя по ошибке прогнать на индексе v2 и наоборот.
- **`scripts/build_eval_dataset_v3.py --parser v2`:** свой кэш, свой `derived_v2/` и свой датасет `data/eval_dataset_v3_parser_v2.json` (раздел 6).

## 5. Поиск на 220 вопросах v3

`research/optimization_5/retrieval.py`, `reports/optimization_5/retrieval/retrieval_v1_v2.json`.

**Методика:**
- Оба индекса собраны здесь одной процедурой (разбор, затем `HybridRetriever.add`, как в `RAGPipeline.ingest_path`) с настройками поиска прогона 1929Z. Поиск теми же моделями на той же GPU (RTX 5060): локальное против локального.
- Доказательство ищется независимо от нарезки и одинаково для обеих версий. Цитата из черновика найдена при k, если в топ-k попал минимальный набор подряд идущих чанков с ней. Для v1 это всегда один чанк, для v2 иногда два: цитата на границе чанков. Разметка таблиц при сравнении игнорируется.
- Recall@k = доля найденных цитат вопроса, hit@k = найдены все. Цитаты нашлись в обеих версиях (0 ненайденных).

| Отвечаемые | n | hit@10 v1 -> v2 | recall@5 v1 -> v2 | recall@1 v1 -> v2 | +/- (hit@10) |
|---|---|---|---|---|---|
| все | 172 | 0.866 -> **0.919** | 0.837 -> 0.907 | 0.584 -> 0.634 | +10 / -1 |
| ответ в таблице | 27 | 0.370 -> **0.704** | 0.407 -> 0.667 | 0.204 -> 0.167 | +9 / -0 |
| ответ в тексте | 145 | 0.959 -> 0.959 | 0.917 -> 0.952 | 0.655 -> 0.721 | +1 / -1 |
| dev | 86 | 0.895 -> 0.965 | 0.884 -> 0.942 | 0.616 -> 0.680 | +6 / -0 |
| test | 86 | 0.837 -> 0.872 | 0.791 -> 0.872 | 0.552 -> 0.587 | +4 / -1 |

- **Гейт:** проходят 47 из 48 неотвечаемых в обеих версиях, отвечаемых отсекает 0 в обеих. Медиана лучшего балла неотвечаемых выросла с 0.323 до 0.389: их контекст выглядит релевантнее, это нужно проверить на галлюцинациях в прогоне с LLM.
- **Объём контекста** (топ-10, символов): медиана 10 204 -> 10 464, максимум 16 581 -> 13 481. Бюджет LLM (8192 токена) не под угрозой.
- **Официальная метрика конвейера** (`evaluate_suite.py retrieval` на датасете v2, ноутбук): Recall@5 0.907, Recall@10 0.948, hit@10 0.965. В прогоне 1929Z на v1 (RTX 3090): 0.837, 0.904, 0.936. Золотые id v1 и v2 - разные наборы чанков, поэтому это подтверждение, а не точное попарное сравнение; попарное - таблица выше.

**По вопросам:** у 49 отвечаемых изменился ранг доказательства, у 41 к лучшему, у 8 к худшему.
- **Найдены после исправления (в топ-10):**
  - таблицы: TC-008, TC-010, TC-014, TC-017, TC-025, MH-022, MH-025, ADV-025, ADV-027;
  - текст: LEX-013.

  Примеры, ранг v1 -> v2:
  - TC-017 (CA/CM в Table 1): вне топ-40 -> 2;
  - MH-022: вне топ-40 -> 2;
  - TC-008 (префикс 01 QUIC): 23 -> 2;

- **Ухудшения внутри топ-10:** MH-039 6 -> 10, остальные на 1-2 места; MH-001: вторая часть (rank 20) выпала из топ-40, recall 0.5 в обеих.

## 6. Датасет v2: требует согласования методики

Индекс v2 состоит из других чанков, а оценка требует, чтобы золотые id датасета были в индексе
(`open_pipeline`). Поэтому есть отдельный датасет `data/eval_dataset_v3_parser_v2.json` с тем
же сборщиком (`--parser v2`). `research.optimization_5.dataset` проверяет его:

**Что совпадает с v1 в 220 из 220 вопросов:** вопрос, эталон, шаблоны оценщика (`answer_must_contain`), ожидаемое поведение, ожидаемый вердикт NLI, цитаты, гипотезы проб NLI.

**Что меняется:**
- `gold_chunk_ids`, `evidence.chunk_ids`, `premise_chunk_id` - id чанков v2;
- у 60 вопросов к HTML путь документа `derived/` -> `derived_v2/` и его `document_id`.

**Отличия правил привязки от v1** (только в режиме `--parser v2`):
1. **Цитата ищется без разметки таблиц** («|», «*»). Черновики цитируют таблицы в формате вывода v1 (`**CA**|||Assessment, ...`), v2 пишет те же ячейки как `| CA | Assessment ... |`. На v1 это правило не меняет ни одной привязки (220 из 220).
2. **Цитата на границе двух чанков** привязывается к паре соседних чанков (в v1 все цитаты лежали в одном чанке). Это 2 вопроса: TC-022 и MH-023.
3. **Правило «доказательства составного вопроса - в разных чанках»** - предупреждение, а не ошибка. Иначе 4 вопроса (MH-015, MH-023, MH-027, MH-029) выпали бы из набора только потому, что чанки v2 крупнее.

Ответы оценщик сравнивает с эталоном по `answer_must_contain`, без id чанков. Правила 1-3 не
влияют на «верно», «галлюцинация» и «ложный отказ». Они влияют на метрики поиска в COMPARISON.md
(Recall по золотым id) и на пробы NLI v3 (их нет в `PLAN=main`).

## 7. Ограничения

- Единственный PDF корпуса - SP 800-53. Правила таблиц PDF (пустые столбцы, объединённые ячейки шапки) проверены на нём и в unit-тестах; на других PDF с многоуровневыми шапками PyMuPDF не размечает уровни шапки, v2 их не восстанавливает.
- Заголовки контролей распознаются по форме SP 800-53 («XX-N» над заглавной строкой). Это правило каталогов контролей, а не общее правило PDF.
- Межъязыковые табличные вопросы (русский вопрос к английской таблице) остаются слабым местом поиска.
- Ответы с LLM на новом индексе ещё не измерены: прирост поиска не гарантирует прироста верных ответов. Это следующий этап (раздел 3 задачи, `EXPERIMENT_PLAN.md`).
