# FactRAG-NLI на RTX 3090 (24 ГБ) под Linux

Поставка ветки `rtx3090-linux`: перенос конвейера с ноутбучной RTX 5060 (8 ГБ, Windows) на
настольную RTX 3090 (Ampere, sm_86, 24 ГБ, драйвер 595, CUDA 13.2) под Linux, замена LLM
Qwen2.5-14B на Qwen3.8-27B, внешний тестовый датасет XQuAD и прогон с отдыхом GPU.

## 1. Что изменилось

| Компонент | Было (RTX 5060 8 ГБ) | Стало (RTX 3090 24 ГБ) |
|---|---|---|
| LLM | Qwen2.5-14B-Instruct Q4_K_M, 25 слоёв на GPU | Qwen3.8-27B UD-Q4_K_XL, все слои на GPU |
| llama.cpp | b10819, Windows | b12002, `ubuntu-cuda-12.8-x64` |
| Окно контекста | 4096 | 8192 |
| Батчи BGE-M3 / реранкера | 2 / 2 | 16 / 8 |
| Реранкер | bge-reranker-large | bge-reranker-large (по умолчанию) или bge-reranker-v2-m3 |
| Запуск | `scripts/start_rag.ps1` | `scripts/linux/*.sh` |

Пороги верификатора и поиска не менялись: они калибровались на dev-половине `eval_dataset_v3`.

Изменения в коде (всё обратно совместимо, умолчания прежние):

- `settings.py`, `generator_verifier.py`: `RAG_LLM_DISABLE_THINKING=true` добавляет к запросу
  `chat_template_kwargs: {"enable_thinking": false}`. Qwen3.x по умолчанию рассуждает в блоке
  `<think>`, который съел бы `max_tokens` и сломал разбор ссылок `[S#]`. Сервер дополнительно
  запускается с `--reasoning off`.
- `evaluate_suite.py`: `FACTRAG_INDEX` и `FACTRAG_PARSE_CACHE` задают индекс и кэш разбора для
  другого датасета (иначе `open_pipeline` перестроил бы индекс v3); `FACTRAG_EMBEDDING_BATCH`
  и `FACTRAG_RERANK_BATCH` поднимают батчи; в `retrieval/cases.jsonl` пишется
  `top_rerank_score` для калибровки гейта.
- `scripts/build_eval_dataset_v3.py`: `parse_all` принимает каталог корпуса и кэша.
- Новые файлы: `scripts/build_xquad_dataset.py`, `scripts/calibrate_gate.py`,
  `scripts/compare_runs.py`, `scripts/linux/`, `.env.rtx3090.example`, тесты
  `tests/test_gpu_duty_cycle.py` и `test_thinking_switch_in_request`.

## 2. Выбор LLM

Кандидаты на октябрь 2026 года, которые помещаются в 24 ГБ вместе с BGE-M3, реранкером и
mDeBERTa (около 3.5 ГБ):

| Модель | Тип | GGUF Q4 | Вывод |
|---|---|---|---|
| **Qwen3.8-27B** (Qwen, 2026-08) | dense 27B, гибрид Gated DeltaNet + attention | 16.4 ГБ (UD-Q4_K_XL) | **выбрана** |
| Qwen3.6-27B (2026-04) | dense 27B | ~16.8 ГБ | предыдущее поколение той же линейки |
| Qwen3.6-35B-A3B | MoE, 3B активных | ~20-22 ГБ | быстрее, но не помещается рядом с кодировщиками |
| Qwen3.8-Flash-Next | MoE | ~200 ГБ | не для одной карты |

Почему Qwen3.8-27B:

- самая новая dense-модель Qwen, помещающаяся целиком на 3090; линейка Qwen остаётся сильнейшей
  открытой по русскому языку и следованию инструкциям (цитаты `[S#]`, отказ при нехватке данных);
- только 16 из 64 слоёв хранят KV-кэш (4 KV-головы по 256), поэтому окно 8192 стоит около
  0.5 ГБ;
- dense, а не MoE: при temperature 0 ответы стабильнее, а скорость (~35 ток/с на 3090) для
  RAG-ответа в 150-300 токенов достаточна.

Режим рассуждений. Qwen3.8 по умолчанию думает перед ответом. Основной профиль `qwen38-27b`
его выключает: ответ короче и быстрее, его проще сравнивать с Qwen2.5. Профиль
`qwen38-27b-think` (те же веса) оставляет рассуждение, ограничивая его 640 токенами
(`--reasoning-budget`) при `RAG_MAX_TOKENS=1024`. Рассуждение приходит в `reasoning_content` и
в ответ и NLI-проверку не попадает. План `full` измеряет оба режима.

Бюджет VRAM: рабочий стол занимает ~0.55 ГБ; Qwen3.8 UD-Q4_K_XL 16.4 ГБ, KV и буферы ~1.5 ГБ,
кодировщики ~3.5 ГБ; итого около 22 ГБ. Профиль `qwen38-27b-q5` (UD-Q5_K_M, 18.4 ГБ) только
без графической оболочки: `sudo systemctl isolate multi-user.target`, управление по SSH.

## 3. Внешний датасет: XQuAD

[google/xquad](https://huggingface.co/datasets/google/xquad) (CC BY-SA 4.0): 240 абзацев
SQuAD v1.1 из 48 статей Википедии и 1190 вопросов с профессиональным переводом на русский;
версии RU и EN параллельны по ID вопроса. `scripts/build_xquad_dataset.py` переводит его в схему
v3, поэтому `evaluate_suite.py` работает с ним без изменений:

- корпус: русские абзацы 40 статей, по файлу `.md` на статью (`data/xquad/docs`); 8 статей
  (выбраны с seed 42) в корпус не входят;
- `single_hop` (158): вопросы по статьям корпуса, половина на русском, половина на английском
  (межъязыковой поиск); цитата-доказательство: русское предложение с ответом, привязанное к
  чанкам тем же кодом, что и v3;
- `unanswerable` (40): вопросы по исключённым статьям, ответ на которые не встречается в корпусе
  (проверено через `absence_terms`);
- NLI-пробы: entailment = предложение с ответом (RU, контроль) и его английская параллель
  (межъязыковая), neutral = предложение исключённой статьи против постороннего предложения
  корпуса;
- проверка ответа: XQuAD даёт короткие фрагменты, а русский их склоняет, поэтому
  `answer_must_contain` содержит одно regex-условие на основы слов фрагмента (RU или EN) в
  любом порядке.

2 кейса из 200 отброшены: их общая цитата попала на границу чанков. Исходные parquet лежат в
`data/xquad/raw`, готовый `data/xquad_dataset.json` в репозитории. `--check` пересобирает и
сверяет его побайтно (так `setup.sh` строит кэш разбора на новой машине).

## 4. Замеры поиска (без LLM, RTX 5060, 2026-10-30)

| Датасет | Реранкер, порог гейта | Recall@5 | MRR@10 | Гейт отсекает: невозможные / отвечаемые |
|---|---|---|---|---|
| v3 | bge-reranker-large, 0.05 (production) | 0.820 | 0.761 | 45.8% / 2.3% |
| v3 | bge-reranker-v2-m3, 0.05 | 0.828 | 0.767 | 12.5% / 0.0% |
| v3 | bge-reranker-v2-m3, 0.2082 | 0.799 | 0.756 | 35.4% / 1.7% |
| XQuAD | bge-reranker-large, 0.05 | 0.671 | 0.591 | 62.5% / 16.5% |
| XQuAD | bge-reranker-v2-m3, 0.05 | 0.962 | 0.956 | 97.5% / 3.2% |
| XQuAD | bge-reranker-v2-m3, 0.2082 | 0.905 | 0.899 | 97.5% / 8.9% |

Dense-поиск BGE-M3 и гибрид RRF на XQuAD дают Recall@5 = 1.000: потери создаёт англо-китайский
bge-reranker-large, который на русском тексте поднимает наверх чужие чанки. Многоязычный
bge-reranker-v2-m3 устраняет это, но его шкала баллов другая: при пороге 0.05 гейт пропускает
почти все невозможные вопросы v3. `scripts/calibrate_gate.py` подобрал 0.2082 на dev-половине v3
по той же доле ложных отказов, что у bge-reranker-large; на test-половине v3 гейт отсекает те же
40.9% невозможных вопросов при 2.3% ложных отказов (было 3.4%). Цена: меньший Recall на XQuAD.

Первый прогон на 3090 оставлял по умолчанию bge-reranker-large; после него основным стал
bge-reranker-v2-m3 с гейтом по лучшему чанку (раздел 5).

NLI-пробы XQuAD (mDeBERTa, правило production): neutral-пробы пойманы в 82.5%, ложное отклонение
entailment-проб 9.8%, совпадение статусов 84.8% (n = 396).

## 5. Прогон 20261030T1420Z на 3090 и что изменено после него

Итог прогона (`PLAN=full`, XQuAD 198, verifier v2), доля верных ответов FactRAG:

| Конфигурация | v3 | XQuAD | Ошибок |
|---|---|---|---|
| qwen38-27b + bge-reranker-large | 78.6% | 65.2% | 0 |
| qwen25-14b + bge-reranker-large | 79.1% | 68.2% | 0 |
| qwen38-27b + bge-reranker-v2-m3 | 75.0% (n = 68) | 73.6% (n = 53) | 152 + 145 |
| qwen38-27b-think + bge-reranker-large | 82.7% (n = 75) | 49.0% (n = 51) | 145 + 147 |

**Ошибки.** В обеих поздних конфигурациях отказали все запросы к LLM после примерно 55-го кейса
v3: без ошибок прошли только кейсы, отсечённые гейтом до генерации (на XQuAD их число точно
совпадает с отсечениями гейта из таблицы поиска). Это картина упавшего llama-server: каждый
следующий запрос мгновенно получает отказ соединения, стадии повтора тоже, потому что сервер
никто не перезапускал. Причину падения установить нельзя: лог сервера перезаписывался при
каждом перезапуске. Что сделано:

- сторож в `evaluate_suite.py` (`FACTRAG_LLM_RECOVER_CMD`, его задаёт `run_benchmark.sh`): перед
  первым кейсом и после каждой ошибки проверяет `/health`; если сервер не отвечает, запускает
  `llama_server.sh ensure` и повторяет кейс; 5 ошибок подряд при живом сервере завершают стадию
  кодом 3 вместо того, чтобы записать ошибкой весь датасет (оставшиеся кейсы выполнит стадия
  повтора);
- `llama_server.sh ensure`: перезапускает сервер, только если он не отвечает, и перед этим
  печатает хвост его лога, `free -m` и занятость GPU; сервер запускается в собственной сессии
  (`setsid`), лог дописывается между перезапусками и в конце прогона копируется в
  `reports/runs/<RUN_ID>/llama-server.log`;
- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` для процессов оценки рядом с ~18 ГБ сервера.

**Главная потеря качества - фильтр по порогу на каждом чанке.** Порог реранкера отсекал не
только вопрос целиком (гейт), но и каждый отдельный чанк ниже порога, поэтому верный чанк с
низким баллом выпадал из контекста LLM за уверенным отвлекающим. Повторный поиск на ПК
разработки (те же цифры, что и на 3090) показал, что до порога XQuAD находит нужный чанк в топ-5
в 94.9% (large) и 100% (v2-m3) случаев. Новая настройка `RAG_RERANK_GATE_SCOPE=top`: порог
решает только отказ по лучшему чанку, а в LLM уходят top_k чанков по рангу. Порог v2-m3 выбран
на dev-половинах обоих датасетов из расчёта, что отсечённый отвечаемый вопрос - почти верная
потеря, а пропущенный невозможный LLM в ~95% случаев сама отклоняет (галлюцинаций на XQuAD
0 из 40): 0.02.

| Поиск (контекст LLM, R@5) | v3 | XQuAD | гейт: отвечаемые отсечены | гейт: невозможные отсечены |
|---|---|---|---|---|
| large, 0.05, порог на каждом чанке (прогон 1420Z) | 0.820 | 0.671 | 2.3% / 16.5% | 45.8% / 62.5% |
| v2-m3, 0.2082, порог на каждом чанке (прогон 1420Z) | 0.799 | 0.905 | 1.7% / 8.9% | 35.4% / 97.5% |
| **v2-m3, 0.02, гейт по лучшему чанку (новое)** | **0.837** | **0.987** | 0% / 1.3% | 2.1% / 97.5% |

Строки 1420Z: v3 / XQuAD через косую черту в последних двух столбцах. На v3 гейт теперь почти
не отсекает невозможные вопросы: их отклоняет LLM (в 1420Z галлюцинации v3 были 5.4% при
отсечении 45.8%, это проверит новый прогон).

**10 чанков в контексте вместо 5.** До порога v2-m3 на v3 находит доказательства в топ-10 в 90.1%
случаев против 83.7% в топ-5: у 16 вопросов (половина многошаговые) нужный чанк стоит на местах
6-10. A/B на ПК разработки с Qwen3.8 без рассуждений (v3, 40 кейсов: эти 16, 12 невозможных и
12 с ложной предпосылкой; всё остальное одинаково):

| top_k | 16 кейсов с доказательством на местах 6-10 | 24 невозможных и с ложной предпосылкой | галлюцинаций | генерация, p50 |
|---|---|---|---|---|
| 5 | 4 верно | 24 верно | 1 | 18 с |
| **10** | **13 верно** | 24 верно | 0 | 31 с |

Ни один кейс не стал хуже. Контроль на обычных отвечаемых вопросах, у которых доказательство уже
в топ-5 (20 случайных кейсов v3): 16 верно и при 5, и при 10 чанках (один кейс выиграл, один
проиграл), то есть длинный контекст не мешает. На 3090 генерация без рассуждений ~3 с, так что
цена - секунды.

**«Нет,» перед исправлением.** Qwen3.8 начинает поправку ложной предпосылки словами «Нет, ...»
(12 утверждений в 33 ответах; у Qwen2.5 - 2 в 220), и mDeBERTa читает лишнее отрицание как
противоречие источнику: «Нет, в RFC 9110 статусный код 413 называется «Content Too Large»»
отклонялось. `RAG_NLI_STRIP_VERDICT_PREFIX=true` убирает вводное «Нет,»/«No,» из гипотезы NLI
(опубликованный текст не меняется), если после него идёт полное утверждение. Replay черновиков
Qwen3.8: 3 верных исправления подтверждены вместо отклонения, 2 перешли из противоречия в
неподтверждённые, галлюцинаций не прибавилось; на 220 черновиках Qwen2.5 (2139Z) не изменилось
ничего. Ступень `verdict_prefix` добавлена в лестницу абляции `evaluate_suite replay`.

**Синтаксис ABNF с подписью.** Qwen3.8 пишет определения как «ABNF-определение delay-seconds:
delay-seconds = 1*DIGIT [S1]». Проверка дословного фрагмента синтаксиса брала всю ASCII-строку
вместе с подписью «delay-seconds:», которой в источнике нет, и mDeBERTa отклонял верный ответ.
Теперь кандидатом служит и часть после «: ». В контрольной выборке это вернуло 1 верный ответ
(V3-TC-001); replay 220 черновиков Qwen2.5 (2139Z) дал те же 173 верных и 5 галлюцинаций.

**Что осталось.** В контрольной выборке черновик Qwen3.8 верен в 20 из 20 кейсов, опубликованный
ответ - в 16: mDeBERTa принимает за противоречие длинные пересказы условий вопроса, а якорная
защита отсекает номера битов, которые модель вычислила сама. Подбирать пороги по нескольким
кейсам - подгонка; для этого нужны все черновики Qwen3.8 из нового прогона на 3090 (replay
без LLM).

**Профиль по умолчанию после изменений:** bge-reranker-v2-m3, `RAG_RERANK_GATE_SCOPE=top`,
порог 0.02 (после прогона 1814Z - 0.005, раздел 6), `RAG_RERANK_TOP_K=10`, `RAG_NLI_STRIP_VERDICT_PREFIX=true`; `PLAN=full` прогоняет qwen38-27b, qwen38-27b-think и qwen25-14b с v2-m3 и для
сравнения qwen38-27b с bge-reranker-large; `XQUAD=full` (1307 вопросов) по умолчанию.

## 6. Прогон 20261030T1814Z (PLAN=main) и что изменено после него

Итог `qwen38-27b + bge-reranker-v2-m3` на 1307 вопросах, ошибок 0:

| Датасет | Черновик LLM верен | FactRAG верен | Галлюцинации | Отказы на отвечаемых |
|---|---|---|---|---|
| v3 | 88.6% (195/220) | 82.7% (182/220) | 1.1% (1/93) | 16.5% (21/127) |
| XQuAD full | 81.0% (881/1087) | 79.9% (869/1087) | 0.0% (0/176) | 21.3% (194/911) |

Разбор 218 неверных ответов XQuAD по логам кейсов:

| Причина | Вопросов |
|---|---|
| LLM вернула отказ, хотя нужный чанк был в контексте (в 141 случае - на первом месте) | 146 |
| гейт отсёк вопрос до генерации | 36 |
| опубликованный ответ не совпал с эталоном | 24 |
| верный черновик отклонён проверкой фактов (в 7 случаях повтор после отклонения закончился отказом) | 12 |

**Первая строка системного промпта.** Промпт начинался словами «Ты анализируешь
нормативно-технические документы»; на статьях Википедии Qwen3.8 без рассуждений отказывала даже
на «Кто проиграл Бронкосу в дивизионном раунде?» при источнике «Бронкос победил Питтсбург Стилерс
в дивизионном раунде». Повторная генерация на ПК разработки на точных контекстах из лога (тот же
GGUF, температура 0, seed 42; воспроизводит отказы 3090): 16 случайных отказов с нужным чанком на
первом месте и 10 контрольных вопросов без ответа или с ложной предпосылкой (4 XQuAD, 6 v3).

| Первая строка и правила | Верно из 16 | Контроль: верно из 10 |
|---|---|---|
| «Ты анализируешь нормативно-технические документы» (было) | 1 | 10 |
| **«Ты отвечаешь на вопросы строго по предоставленным источникам» (стало)** | **8** | **10** |
| то же + правило «отвечай, если ответ записан иначе, чем в вопросе» | 4 | 10 |
| то же, что «стало», + нейтральная фраза отказа | 8 | 10 |
| то же, что «стало», без абзаца о ложной предпосылке | 9 | 10 |

Фраза отказа не меняется (по ней оценка распознаёт отказ во всех прогонах), абзац о ложной
предпосылке остаётся: он нужен вопросам v3 с ложной предпосылкой, а выигрыш без него - 1 кейс.
Повторный запрос после отказа («перепроверь источники, ответ может быть записан иначе») вернул
ответ в 1 случае из 10 и не принят. Регрессия на v3: см. конец раздела.

**Гейт v2-m3: 0.005 вместо 0.02.** При 0.02 гейт отсёк 36 отвечаемых вопросов XQuAD, а из 10
пропущенных невозможных LLM отклонила все 10. Сквозной прогон на ПК разработки (новый промпт,
тот же поиск) для 45 вопросов XQuAD с лучшим баллом реранкера от 0.005 до 0.02, которые при 0.02
отсекаются целиком: 7 из 23 отвечаемых теперь верны, 22 из 22 невозможных по-прежнему получили
отказ, галлюцинаций 0. На v3 ниже 0.02 только 1 невозможный вопрос.

**Якоря в заголовке раздела** (`RAG_NLI_ANCHOR_HEADINGS=true`, ступень `anchor_headings` в
лестнице replay). Якорная защита искала числа и идентификаторы утверждения только в тексте чанка
без служебного заголовка, а предмет чанка часто назван лишь в заголовке его раздела: «Super Bowl
50», «AC-7», «UUIDv1», «CA-8». Утверждение «Сурдоперевод гимна на Суперкубке 50 выполняла Марли
Мэтлин» отклонялось при P(entailment) = 0.96. Теперь якорь можно найти и в `section_path`
процитированного источника (NLI-посылка этот заголовок уже содержит). Replay черновиков 1814Z:
XQuAD 869 -> 873 верных, v3 без изменений (181, первая попытка), галлюцинаций не прибавилось.

**Инициалы.** Сегментация v2 резала «Уильям Э. Саймон» на два утверждения, и в опубликованный
текст попадали лишние ссылки («Уильям Э. [S1] Саймон [S1]»), а «Мост называется «Джон В. Викс»»
обрезался до «Джон В.»: вторая половина ушла как противоречие. Заглавная буква с точкой перед
заглавной буквой теперь не конец предложения (11 ответов XQuAD 1814Z).

**Сравнение с эталоном для числительных.** Шаблон ответа брал 4-буквенный префикс слова-числа:
«пяти» не совпадало с «пять», «трех» с «три». Теперь число принимается в любом падеже и цифрой
(шаблон - надмножество прежнего). Изменилось 34 шаблона полного набора и 6 стандартного;
пересчёт ответов 1814Z: +2 верных (V3-XQFRU-078, V3-XQFRU-389), других изменений нет.

**Рассуждения только при отказе.** Оставшиеся отказы Qwen3.8 без рассуждений - главный резерв
XQuAD, а режим с рассуждениями отвечает на обращённые вопросы. `PLAN=full` прогоняет обе
конфигурации на тех же вопросах, и `COMPARISON.md` теперь добавляет расчётную строку
«thinking only on refusal»: кейс, в котором первый черновик без рассуждений - отказ, берёт исход
конфигурации с рассуждениями (тот же поиск, промпт и seed, поэтому это ровно тот вызов, который
сделал бы такой гибрид). По 1814Z рассуждение понадобилось бы в 63 вопросах v3 и 155 XQuAD.

## 7. Что проверено до отправки (ПК разработки: RTX 5060 Laptop 8 ГБ, Windows)

На этом ПК нет Linux и нет 24 ГБ, поэтому качество на 3090 здесь не измерено: его покажет
`run_benchmark.sh`. Проверено следующее:

- GGUF Qwen3.8-27B UD-Q4_K_XL скачан, SHA-256 совпал с опубликованным; модель загружается в
  llama.cpp (установленная b10819: 16 слоёв на GPU, остальное в RAM).
- Сборка b12002 (Windows CUDA 12.4, тот же коммит, что и Linux-архив) видит CUDA-устройство; флаги
  `-fa on`, `--cache-ram`, `--reasoning off`, `--reasoning-budget` в ней есть.
- Отключение рассуждений: тот же вопрос дал верный ответ с `[S1]` за 25 токенов вместо 130
  (105 ушли на скрытые рассуждения).
- Сквозной прогон `evaluate_suite e2e` с Qwen3.8 (по 4 кейса, без ошибок, без утечки `<think>`):
  v3 3 из 4 верно; XQuAD 2 из 4 с bge-reranker-large (в двух других нужный чанк не попал в
  источники). С bge-reranker-v2-m3 чанк попадает, но Qwen3.8 без рассуждений отказывает на

  На 4 кейсах это наблюдения, а не оценка качества.
- Тесты проекта: 263 прошли, 1 пропущен (заморозка стадии через SIGSTOP проверяется только на

## 9. Прогон с отдыхом GPU

```bash
bash scripts/linux/run_benchmark.sh                 # PLAN=full, XQUAD=full (~9 ч с отдыхом)
PLAN=main bash scripts/linux/run_benchmark.sh       # только основная конфигурация (~1 ч)
PLAN=quick bash scripts/linux/run_benchmark.sh      # 10 кейсов на датасет, проверка за ~15 мин
bash scripts/linux/run_benchmark.sh --resume        # продолжить после остановки или перезагрузки
bash scripts/linux/stop_benchmark.sh                # остановить прогон и llama-server
XQUAD=standard bash scripts/linux/run_benchmark.sh  # прежние 198 вопросов XQuAD
```

`XQUAD=full` (по умолчанию) берёт все 1087 подходящих вопросов XQuAD (911 с ответом, 176
отказов; `data/xquad_dataset_full.json`, сборка `build_xquad_dataset.py --full`), вместе с v3
1307 вопросов на конфигурацию. `XQUAD=standard` - выборка из 198 вопросов (по 4 на статью
корпуса и по 5 отказов на исключённую статью), набор прогона 20261030T1420Z. Результаты полного
набора пишутся в подкаталоги `xquad-full`, а `COMPARISON.md` добавляет строку `all` с долями по
сумме вопросов. Вместе с `--resume` переменные `PLAN` и `XQUAD` переключают уже идущий прогон:
готовые кейсы сохраняются, оставшиеся стадии идут по новому выбору. После смены настроек поиска
(разделы 5 и 6) начинайте новый прогон, а не `--resume` старого: иначе в одной папке окажутся кейсы
с разными настройками.

Прогон отвязан от терминала (`setsid nohup`): закрытие AnyDesk или окна его не прерывает,
Ctrl+C прекращает только просмотр лога. Каждые 45 минут работы `gpu_duty_cycle.py`
замораживает текущую стадию (SIGSTOP) на 5 минут и затем продолжает её (SIGCONT). Отдых
начинается и раньше, если GPU нагрелся до 83 °C. llama-server не замораживается: он дописывает
начатый ответ, и клиент получает его после паузы без таймаута. Параметры: `WORK_MINUTES`,
`REST_MINUTES`, `GPU_TEMP_LIMIT`.

План `full` (оценка по скоростям прогона 1420Z: ~8 ч работы и ~1 ч отдыха; основная часть -
Qwen3.8 с рассуждениями, ~18 с на запрос против ~2-3 с без них):

1. проверка датасета XQuAD, NLI-пробы XQuAD;
2. поиск v3 и XQuAD для каждого реранкера;
3. для каждой конфигурации (`qwen38-27b+bge-reranker-v2-m3`, `qwen38-27b-think+bge-reranker-v2-m3`,
   `qwen25-14b+bge-reranker-v2-m3`, `qwen38-27b+bge-reranker-large`): llama-server с нужной
   моделью (`llama_server.sh ensure`: уже работающий сервер того же профиля не перезапускается),
   e2e v3 (220), e2e XQuAD (1087 или 198), повтор кейсов с инфраструктурными ошибками;
4. остановка сервера, копия его лога в папку прогона и `COMPARISON.md`.

Результаты: `reports/runs/<RUN_ID>/COMPARISON.md`; полные логи кейсов в подкаталогах.
Состояние во время работы: `.artifacts/duty_cycle/status.json` (стадия, работа/отдых,
температура, мощность, VRAM). Лог: `reports/runs/<RUN_ID>/benchmark.log`.

Как читать сравнение: строка `qwen25-14b+bge-reranker-v2-m3` показывает старую модель на том же
железе, с тем же кодом и поиском, поэтому разница с `qwen38-27b+bge-reranker-v2-m3` целиком
относится к LLM; строка `qwen38-27b+bge-reranker-large` - к реранкеру. Строка-эталон с ноутбука
(20261026T2139Z_v3) получена верификатором v1; replay тех же черновиков верификатором v2 дал 78.6%.

## 11. Перенос на другой ПК

Архив `FactRAG-NLI-3090.zip` (папка `FactRAG-NLI-rtx3090-linux`) содержит код, данные и отчёты
без моделей и `.venv`: их ставит `setup.sh`. Источники с одинаковым содержимым: Google Диск,
https://github.com/EGRNEGR/FactRAG-NLI/archive/refs/heads/rtx3090-linux.zip или
`git clone -b rtx3090-linux`. Архив собран `git archive`, bash-скрипты в нём с LF и правом
на исполнение.

Обновление распакованной копии без git: `bash scripts/linux/update.sh`. Скрипт скачивает архив
ветки с GitHub, перечисляет изменённые файлы и перезаписывает их; `models/`, `.venv/`, `tools/`,
`.artifacts/`, `.env` и результаты в `reports/runs/` не затрагиваются. Во время прогона скрипт не
работает (сначала `stop_benchmark.sh`). Журнал обновлений: `.artifacts/update/history`.

## 12. Неполадки

| Симптом | Что делать |
|---|---|
| `CUDA out of memory` при старте llama-server | закрыть браузер; `LLAMA_CTX=6144`; без GUI: `sudo systemctl isolate multi-user.target` |
| `llama-server does not see a CUDA device` | `nvidia-smi`; переустановить драйвер; `rm -rf tools/llama` и снова `setup.sh` |
| загрузка модели оборвалась | повторить `setup.sh`: curl продолжит с места обрыва |
| `SHA-256 ... FAILED` | удалить файл из `models/llm` и повторить `setup.sh` |
| много `errors` в e2e | `grep -n watchdog reports/runs/<RUN_ID>/benchmark.log`; лог сервера: `.artifacts/llama/server.log` (дописывается между перезапусками); затем `run_benchmark.sh --resume` |
| стадия e2e завершилась кодом 3 | 5 ошибок подряд при живом сервере: текст ошибки в `benchmark.log`, строка `stage stopped`; оставшиеся кейсы выполнит стадия повтора или `--resume` |
| GPU постоянно > 83 °C | проверить обдув; `GPU_TEMP_LIMIT=80 WORK_MINUTES=30` |
