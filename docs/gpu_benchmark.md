# GPU и этап 11

## Режим моделей

`RAG_MODEL_DEVICE=auto` (по умолчанию) выбирает CUDA, если она доступна.
`cuda` / `cuda:0` требуют доступной CUDA; явный `cpu` сохраняется.
`RAG_MODEL_PRECISION=auto` выбирает BF16 на поддерживаемой GPU, иначе FP16;
на CPU используется FP32. Можно явно задать float16/bfloat16/float32.
Production не подменяет ошибки загрузки или OOM эвристической моделью/CPU.
Для SentenceTransformer, реранкера и NLI включён `torch.inference_mode()`;
вероятности классификаторов вычисляются в FP32 после reduced-precision inference.

`RAG_LLM_API_STREAM=true` включает потоковую генерацию. По умолчанию прежний
непотоковый HTTP-контракт сохранён; benchmark включает потоковый режим сам.
`llm_ttft_ms` измеряется от отправки streaming POST до первого непустого content
delta, включая транспорт и ожидание сервера. Это клиентский TTFT, не внутренний
CUDA kernel time. При непотоковом ответе метрика отсутствует, а не равна нулю.
`generation_ms` включает полный вызов генератора, включая подготовку промпта.
Поиск и реранкинг разделены; перенос результатов тензоров на CPU завершает
GPU-вычисления до окончания таймера. Инициализация моделей учитывается отдельно.

## Воспроизводимый запуск

С уже работающим локальным llama-server, настройками production и локальными весами:

```powershell
.\.venv\Scripts\python benchmark.py --output .artifacts\gpu-run-new --documents 3 --repeats 3
```

Выходной каталог должен быть новым. Скрипт создаёт отдельные документы и индекс,
сохраняет `report.json`, возвращает 0 при прохождении проверок и 1 при ошибке.
Параметры прогона: CUDA, батчи по 2, контекст сервера 4096, максимум ответа 128.
Параметры основного корпуса и `.env` не изменяются. Для стресс-проверки необходим
локальный llama.cpp endpoint `/tokenize`; другие OpenAI-совместимые серверы могут
поддерживать обычные запросы, но не эту часть диагностики.

Сначала выполняется короткий сквозной запрос. Затем, при загруженных BGE/NLI и
работающем llama-server, индексируются длинные документы и повторяются запросы.
Отдельные длинные HTTP-промпты обходят консервативный byte-limit упаковщика RAG,
чтобы проверить фактические 3,8k входных токенов по `usage` сервера. Это отдельный
стресс контекста LLM, не утверждение, что RAG-упаковщик отправил все 4k токенов.

VRAM: с интервалом 50 мс измеряется свободная память всей карты (включая
llama-server и другие процессы). Пики PyTorch allocated/reserved относятся только
к Python-процессу. Короткие пики между отсчётами могут быть пропущены.
Проверяется совместное размещение моделей; многопользовательская конкурентная
нагрузка этим последовательным прогоном не моделируется.

## Результат 2026-09-05

- PyTorch `2.12.0.dev20260408+cu128`; RTX 5060 Laptop, capability `(12, 0)`.
- Все три transformer-модели: `cuda:0`, `torch.bfloat16`, проверено по параметрам.
- Существующий llama-server: `-ngl 35 -c 4096 --port 8080`.
- 3 длинных документа → 42 чанка; индексация около 1,72 с с уже загруженными моделями.
- 3 последующих RAG-запроса: p50 5,127 с; p95 6,148 с. Выборка мала и синтетическая.
- TTFT этих запросов: 1038 / 420 / 499 мс. Поиск: 16–29 мс;
  реранкинг: 710–748 мс; NLI: 347–610 мс. Результаты зависят от длины контекста.
- Стресс LLM: по 3803 входных + 16 выходных токенов, три успешных ответа без OOM.
  Первый TTFT около 9,53 с; повторные 105/94 мс используют одинаковый промпт
  и могут выигрывать от серверного KV/prompt cache. Это не сравнение CPU/GPU.
- Минимальная свободная VRAM: 1 690 513 408 байт (~1,57 GiB).
  Наблюдаемый пик занятой памяти всей карты ~6,39 GiB;
  PyTorch peak allocated ~2,68 GiB, reserved ~2,70 GiB.
- Вопрос про шоколадный торт: канонический отказ примерно за 34 мс, без LLM/NLI.
- Пустой текст на входе верификатора: канонический отказ.
  Два противоречащих цитируемых источника: отказ с реальным NLI (~249 мс).
  Эти два кейса используют управляемый текст генерации, а не случайный ответ LLM.
  Пустой/оборванный HTTP-stream считается ошибкой протокола и не принимается за факт.

Доказательства: `.artifacts/gpu-benchmark-01/report.json`, `.artifacts/gpu-smoke.json`.
Это диагностика задержек и VRAM; не оценка качества по экспертному корпусу и
не гарантия отсутствия OOM при больших батчах, иной нагрузке или иных настройках.
