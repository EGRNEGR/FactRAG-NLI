**Локальная RAG-система для технической документации, которая не публикует утверждения LLM без подтверждения источником.**
Ответ со ссылками на источники генерирует Qwen3.8-27B, затем каждое утверждение проверяет логистический судья над двумя NLI-моделями (mDeBERTa-v3 и BGE-M3-zeroshot) с детерминированным контролем чисел и идентификаторов. Неподтверждённое удаляется, а после отказа контур делает повторные проходы и публикует их результат, только если он проверен полностью. Весь конвейер работает на одной RTX 3090 без внешних API.

**Итог (прогон `20261104T1222Z`, 1307 вопросов: технический набор v3 и XQuAD):** 91,3 % верных ответов против 86,7 % у черновика того же генератора (+68/−8 вопросов, точный тест Мак-Немара p = 5,6·10⁻¹³), галлюцинации 0,7 % (2 из 269), ложные отказы 6,7 %, медиана полного ответа 4,4–6,1 с.

## Как это работает

```mermaid
graph TD
    Q["Вопрос"] --> N["Нормализация NFKC,<br/>фильтр prompt-injection"]
    N --> D["Dense: BGE-M3 → Qdrant<br/>top-60"]
    N --> S["Sparse: BM25Okapi<br/>top-60"]
    D --> F["Взвешенный RRF, k = 30<br/>вес BM25 × доля терминов запроса в словаре"]
    S --> F
    F --> R["bge-reranker-v2-m3, 40 кандидатов<br/>0.2·RRF + 0.8·rerank"]
    R --> G1{"rerank ≥ 0.005?"}
    G1 -- "нет" --> T{"Вопрос на другом языке,<br/>чем источники?"}
    G1 -- "да" --> C["Контекст: top-10 фрагментов S1…S10,<br/>окно 8192 токена"]
    C --> L["Qwen3.8-27B UD-Q4_K_XL<br/>llama-server, без рассуждений, temperature 0"]
    L --> SP["Разбиение черновика на утверждения,<br/>наследование ссылок [Si]"]
    SP --> V["mDeBERTa-v3 + BGE-M3-zeroshot:<br/>утверждение × фрагмент и его окна"]
    V --> J{"Логистический судья, θ = 0.3,<br/>и контроль якорей: числа и<br/>идентификаторы есть в источнике"}
    J -- "все подтверждены" --> O["Ответ с цитатами [Si]"]
    J -- "часть снята" --> TT["llm_think_on_trim: ответ с рассуждением,<br/>принимается только при полной проверке"]
    TT --> O
    J -- "отказ LLM или проверки" --> RT["Повтор с рассуждением; затем<br/>2 черновика при T = 0.7, если rerank ≥ 0.5"]
    RT -- "проверен" --> O
    RT -- "снова отказ" --> T
    T -- "да (G3)" --> TR["Перевод вопроса на язык источников,<br/>повторный поиск и один черновик"]
    TR -- "проверен" --> O
    TR -- "нет" --> X
    T -- "нет" --> X["Типизированный отказ"]
```

Посылкой для NLI служит процитированный фрагмент без служебного заголовка и его окна из 1–2 предложений, дополненные названием документа и раздела. Судья объединяет вероятности следования и противоречия обеих моделей (`data/nli_judge/bge-m3-zeroshot.json`, порог подобран на выборке dev). Контроль якорей работает как жёсткое правило: утверждение с числом, кодом или идентификатором, которого нет в источнике, не публикуется при любой оценке моделей. Структурный разбор parser v2 читает подписи таблиц, сеточные таблицы RFC и заголовки разделов. Подробности по этапам: [optimization_3](reports/optimization_3/FINAL_REPORT.md) (судья, think_on_trim), [optimization_4](reports/optimization_4/FINAL_REPORT.md) (G3), [optimization_5](reports/optimization_5/FINAL_REPORT.md) (parser v2).

## Ключевые возможности

- **Полностью локальный контур.** Модели загружаются только из локальных файлов (`local_files_only`, `trust_remote_code=False`), LLM доступна только по loopback; документы и вопросы не покидают машину.
- **Двухэтапный гибридный поиск.** Dense-векторы BGE-M3 находят перефразировки, BM25 — точные термины, коды и идентификаторы. RRF объединяет кандидатов, а вес BM25 зависит от того, какая доля терминов запроса есть в словаре индекса. Переранжировщик bge-reranker-v2-m3 и гейт релевантности отсекают вопросы вне базы до вызова LLM.
- **Двухмодельная проверка каждого утверждения.** Логистический судья над mDeBERTa-v3 и BGE-M3-zeroshot плюс детерминированный контроль якорей; проверка двумя моделями занимает 0,1–0,2 с на ответ.
- **Восстановление полноты без ослабления проверки.** Рассуждение после отказа и после частичного удаления утверждений, сэмплирование при сильном источнике, перевод вопроса на язык документов (G3). Любой повторный проход публикуется только в полностью проверенном виде.
- **Воспроизводимая оценка.** Замороженное разбиение dev/test (651 / 656 вопросов), пороги подбираются только на dev, точный тест Мак-Немара по каждому вопросу, хеши датасета, кода и весов в каждом прогоне, офлайн-replay сохранённых черновиков без LLM.
- **Документы PDF, DOCX, TXT, Markdown** со структурой разделов и таблиц, инкрементальная загрузка с дедупликацией по SHA-256; интерфейсы Streamlit, FastAPI и CLI.

## Результаты

### Сквозная точность по этапам оптимизации

Полные прогоны на RTX 3090, 1307 вопросов (v3 — 220 технических вопросов по RFC 9110, 9000, 9457, 9562, NIST SP 800-63B-4 и 800-53 Rev. 5, PostgreSQL 18 и PEP 703; XQuAD — 1087 вопросов на русском и английском по параллельному корпусу). «Черновик» — первый ответ того же генератора без проверки.

| Метрика | `0749Z` исходная | `1310Z` якоря, think_on_trim | `1929Z` + G3 | `1222Z` + parser v2 |
|---|---|---|---|---|
| Верно, все 1307 | 90,2 % (1179) | 90,6 % (1184) | 90,9 % (1188) | **91,3 % (1193)** |
| Верно, v3 (220) | 86,4 % (190) | 88,6 % (195) | 88,6 % (195) | **90,9 % (200)** |
| Верно, XQuAD (1087) | 91,0 % (989) | 91,0 % (989) | 91,4 % (993) | 91,4 % (993) |
| Черновик без проверки, все | 86,0 % (1124) | 86,0 % (1124) | 86,1 % (1125) | 86,7 % (1133) |
| Галлюцинации (из 269) | 1,1 % (3) | 1,1 % (3) | 1,1 % (3) | **0,7 % (2)** |
| Ложные отказы (из 1038) | 7,6 % (79) | 7,6 % (79) | 7,1 % (74) | **6,7 % (70)** |
| Попарно к предыдущему | — | +5/−0, p = 0,0625 | +4/−0, p = 0,125 | +11/−6, p = 0,33 |
| Попарно к черновику | +67/−12 | +68/−8 | +70/−7 | **+68/−8, p = 5,6·10⁻¹³** |

Суммарный эффект оптимизации (`1222Z` против `0749Z`) — +18/−4 вопроса, p = 0,0043, поровну на dev (+9/−2) и test (+9/−2). Отдельные шаги значимости не достигают и не могут её достичь: при +4/−0 наименьшее возможное p равно 0,125. Поэтому критерием их принятия служили ноль новых галлюцинаций, ноль потерь ранее верных ответов и одинаковый прирост на dev и test.

### Что даёт проверка, а что — повторные проходы

![Черновик, черновик после проверки и полный контур: верные ответы, ложные отказы, галлюцинации](reports/figures/readme_contour.svg)

Проверка сама по себе точность не повышает. На тех же черновиках она снимает 27 верных ответов (+0/−27) и переводит их в отказы. Выше черновика контур поднимают повторные проходы: +88/−1 к проверенному черновику, итог +68/−8 к исходному. Число галлюцинаций на финальном генераторе мало при любом методе (1–2 из 269), поэтому безопасность методов проверки сравнивается на стресс-наборе. Данные: [`reports/review/significance.json`](reports/review/significance.json).

### Второй генератор

![Действие верификатора на черновиках Qwen2.5-14B-Instruct и Qwen3.8-27B](reports/figures/readme_generators.svg)

На черновиках Qwen2.5-14B-Instruct (набор v3) судья снимает 5 галлюцинаций из 10 и не добавляет новых, теряя 18 верных ответов; одиночный NLI-фильтр снимает те же пять ценой 58. Направление эффекта одинаково на обоих генераторах, но при +5/−0 точный тест даёт p = 0,0625, поэтому вывод остаётся качественным ([`second_generator.json`](reports/review/second_generator.json)).

### Поиск, время и разметка

- **Поиск:** XQuAD — Recall@5 0,981, MRR@10 0,966, гейт отклоняет 81,8 % неотвечаемых вопросов и 1,4 % отвечаемых; v3 — parser v2 поднял Recall@5 с 0,837 до 0,907 и MRR@10 с 0,769 до 0,824.
- **Время на RTX 3090:** медиана полного ответа 6,1 с на v3 и 4,4 с на XQuAD; генерация занимает 89–91 % времени, поиск, переранжирование и проверка вместе — меньше 0,5 с. Пиковая видеопамять — до 21,9 ГБ из 24, полный прогон 1307 вопросов идёт около трёх часов.
- **Разметка v3:** все 220 вопросов проверены вручную, согласие автоматического оценщика с экспертом 217 из 220, κ Коэна = 0,912 ([`reports/review/audit`](reports/review/audit)).

## Быстрый старт (RTX 3090, Linux)

Проверено на Ubuntu 24.04 с RTX 3090 (24 ГБ, sm_86), llama.cpp b12002 (`ubuntu-cuda-12.8-x64`). Полное руководство: [`docs/RTX3090_LINUX.md`](docs/RTX3090_LINUX.md).

```bash
git clone https://github.com/EGRNEGR/FactRAG-NLI.git
cd FactRAG-NLI
bash scripts/linux/setup.sh                        # venv, PyTorch, llama.cpp, модели (~34 ГБ), .env, тесты
bash scripts/linux/llama_server.sh start           # профиль qwen38-27b-hybrid; status | stop | restart
PLAN=quick bash scripts/linux/run_benchmark.sh     # 10 вопросов на датасет, ~15 мин
PLAN=main bash scripts/linux/run_benchmark.sh      # итоговая конфигурация на 1307 вопросах, ~3,5 ч
bash scripts/linux/run_benchmark.sh --resume       # продолжить после остановки или перезагрузки
bash scripts/linux/stop_benchmark.sh               # остановить прогон и llama-server
```

Копия без git обновляется из ветки `main` командой `UPDATE_BRANCH=main bash scripts/linux/update.sh`. Модели, `.venv`, `.env` и результаты прогонов при обновлении не затрагиваются. Отдельные механизмы отключаются переменными `THINK_RETRY=off`, `THINK_ON_TRIM=false`, `RECOVERY=off`, `QUERY_TRANSLATION=off`, `PARSER=v1`, а `VERIFIER=rules` возвращает верификатор v2 на правилах.

Модульные тесты не требуют весов моделей и GPU:

```bash
python -m pytest
python -m ruff check .
python -m mypy --strict .
```

## Ограничения

- Проверка утверждений сама по себе переводит ошибки из галлюцинаций в отказы, а не повышает точность; прирост над черновиком создают повторные проходы (см. [Результаты](#что-даёт-проверка-а-что--повторные-проходы)).
- Подмену ответа другой сущностью того же абзаца не распознаёт ни один из проверенных методов: судья пропускает 26,6 % таких утверждений, потому что новая сущность есть в источнике. Остаются трудными модальные конструкции (MUST / SHOULD), отрицания и привязка значения к нужной строке таблицы.
- Гейт релевантности на v3 не отсекает неотвечаемые вопросы: они относятся к тем же документам (смежный раздел, ложная предпосылка, другая версия стандарта). Их удерживают отказ генератора и верификатор.
- Разметку v3 вручную проверил один эксперт; независимая перекрёстная разметка не проводилась. Полный прогон контура выполнен с одним генератором, второй (Qwen2.5-14B-Instruct) проверен только на сохранённых черновиках.
- Вердикт верификатора не гарантирует фактической точности: NLI-модели ошибаются в обе стороны.
- Сканированные PDF без текстового слоя (OCR) и формат `.doc` не поддерживаются. Интерфейс рассчитан на доверенную локальную машину: многопользовательской авторизации в Web нет.

## История: прототип на GPU 8 ГБ

Первая версия работала на RTX 5060 Laptop (8 ГБ, Windows) с Qwen2.5-14B-Instruct Q4_K_M, bge-reranker-large и одиночным mDeBERTa-v3 и давала на наборе v3 75,5 % верных ответов при медиане ответа 21,4 с. Итоговая конфигурация на том же наборе даёт 90,9 % при 6,1 с. Сравнение отражает совокупную смену генератора, переранжировщика, верификатора и оборудования, а не вклад отдельных компонентов.

<details>
<summary>Запуск и конфигурация прототипа (Windows, GPU 8 ГБ)</summary>

Проверено на Windows 11, Python 3.12, NVIDIA RTX 5060 Laptop (sm_120).

#### 1. Окружение

```powershell
git clone https://github.com/EGRNEGR/FactRAG-NLI.git
cd FactRAG-NLI
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install "transformers>=4.40" httpx==0.28.1
```

PyTorch с CUDA устанавливается отдельно; для RTX 50xx нужна сборка с поддержкой sm_120 (проверено: `2.12.0.dev20260408+cu128`, см. [`docs/evidence/release_runtime.txt`](docs/evidence/release_runtime.txt)). Проверка реального вычисления на GPU:

```powershell
python -c "import torch; x=torch.randn(64,64,device='cuda'); print(torch.__version__, (x@x).shape)"
```

#### 2. Веса моделей

| Каталог | Источник |
|---|---|
| `models/bge-m3` | [BAAI/bge-m3](https://huggingface.co/BAAI/bge-m3) |
| `models/bge-reranker-large` | [BAAI/bge-reranker-large](https://huggingface.co/BAAI/bge-reranker-large) |
| `models/mdeberta-nli` | [MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7](https://huggingface.co/MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7) |
| `models/llm/Qwen2.5-14B-Instruct-Q4_K_M.gguf` | [Qwen/Qwen2.5-14B-Instruct-GGUF](https://huggingface.co/Qwen/Qwen2.5-14B-Instruct-GGUF) |

`llama-server.exe` и его DLL из [релиза llama.cpp](https://github.com/ggml-org/llama.cpp/releases) помещаются в `tools/llama/`. Веса и бинарники в репозиторий не входят; порядок доставки и сверки хешей описан в [`docs/RELEASE_GUIDE.md`](docs/RELEASE_GUIDE.md). Аудит окружения: `python scripts/verify_environment.py`.

#### 3. Конфигурация

```powershell
Copy-Item .env.example .env
python -c "import json, secrets; print(json.dumps([secrets.token_urlsafe(48)]))"   # значение для RAG_API_TOKENS
```

`.env.example` содержит профиль, на котором получены опубликованные метрики.

#### 4. LLM-сервер

```powershell
.\tools\llama\llama-server.exe -m .\models\llm\Qwen2.5-14B-Instruct-Q4_K_M.gguf -ngl 25 -c 4096 -b 128 -ub 64 -np 1 --cache-ram 0 --port 8080 --host 127.0.0.1
```

`-ngl 25` подобран замером на RTX 5060 Laptop 8 ГБ: рядом с llama-server на GPU работают BGE-M3, реранкер и NLI (около 2.7 ГБ в процессе PyTorch). Прежний профиль `-ngl 35` с llama.cpp сборки 10819 в 8 ГБ вместе с ними не помещается: драйвер Windows вытесняет часть буферов llama-server в общую память, и со второго запроса обработка промпта замедляется примерно в 4 раза; при 25 слоях скорость стабильна. Таблица замеров: [отчёт, раздел 6](reports/EVALUATION_REPORT.md#6-задержки-и-ресурсы). `.\scripts\start_rag.ps1` запускает сервер с тем же профилем; прежний задаётся параметром `-GpuLayers 35`.

`--cache-ram 0` отключает кэш промптов в ОЗУ (в сборке 10819 он по умолчанию до 8 ГиБ): при сотнях разных вопросов он не даёт повторного использования, а рост памяти выталкивает CPU-слои модели из ОЗУ. Флаг поддерживается только новыми сборками llama.cpp.

#### 5. Индексация и запуск

```powershell
python baseline_rag.py --index ./data/documents            # индексировать каталог документов
python scripts/manage_index.py --add "C:\Docs\manual.pdf"  # добавить файл инкрементально
.\scripts\start_rag.ps1                                    # llama-server + Streamlit: http://127.0.0.1:8501
uvicorn api:app --host 127.0.0.1 --port 8000               # или HTTP API: /health, /ingest, /query
python demo.py --query "Что означает код HTTP 204 согласно RFC 9110?" --ensure-index
.\scripts\stop_rag.ps1 -Force                              # остановить llama-server
```

Встроенный Qdrant допускает одного владельца индекса: Web, API, CLI и оценку над одним индексом одновременно не запускают. Подробное руководство по эксплуатации: [`docs/OPERATIONS.md`](docs/OPERATIONS.md).

#### 6. Тесты и оценка

```powershell
python -m pytest                       # модульные тесты без весов моделей и GPU
python -m ruff check .
python -m mypy --strict .

python scripts/build_eval_dataset_v3.py --check                    # проверить датасет v3
python evaluate_suite.py --run-dir reports/runs/my-run retrieval   # абляция поиска (без LLM)
python evaluate_suite.py --run-dir reports/runs/my-run nli         # NLI на контрольных парах
python evaluate_suite.py --run-dir reports/runs/my-run e2e --profile guard_on

```

Прогон фиксирует seed, параметры сэмплирования, пороги NLI, хеши датасета, кода и весов, командную строку llama-server и пишет сырые логи по каждому кейсу; прерванный режим продолжается с последнего кейса.
