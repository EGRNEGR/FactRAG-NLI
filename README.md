# Local RAG Platform

Локальный программный комплекс Retrieval-Augmented Generation предназначен для поиска и формирования ответов по нормативной и технической документации. Архитектура объединяет структурную обработку документов, гибридное извлечение контекста, переранжирование и пофразовую NLI-верификацию. Реализованы Web-интерфейс, инкрементальная индексация и отдельный режим саммаризации.

Инференс выполняется локально после предварительной установки зависимостей и размещения весов моделей. Результаты корпусной оценки и ограничения вероятностной верификации приведены отдельно от инструкций эксплуатации.

## Web-интерфейс

Основной интерфейс реализован на Streamlit. Запуск выполняется из корня проекта:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[web]"
.\scripts\start_rag.ps1
```

Интерфейс доступен по адресу `http://127.0.0.1:8501`. Скрипт проверяет состояние локального llama-server, при необходимости запускает его с профилем `-ngl 35 -c 4096 -b 128 -ub 64 -np 1`, ожидает готовности, проверяет индекс и выполняет `python -m streamlit run app.py` с привязкой к loopback-адресу. Параметры `-IndexOnly`, `-Query`, `-Preset` и `-Export` сохранены для соответствующих сценариев. Параметр `-Cli` запускает демонстрационный интерфейс `demo.py`.

В боковой панели выбирается режим поиска ответа или саммаризации. В режиме QA вводится вопрос. Для саммаризации документ выбирается из списка либо указывается его точное имя или идентификатор. Поддерживается загрузка PDF с текстовым слоем, TXT, Markdown и DOCX размером до 20 МБ. Дубликаты определяются по SHA-256; новые файлы сохраняются в `data/documents/uploads/<sha256>/`.

Основной результат отображается в чате. Извлечённый контекст, NLI-статусы и время стадий доступны в раскрываемых блоках. Итоговый текст передаётся в чат после проверки; непроверенные токены не публикуются в качестве готового ответа. В режиме саммаризации допускается NEUTRAL, что соответствует менее строгой политике верификации. Вероятностная NLI-проверка не гарантирует фактической точности.

Общий экземпляр `WebBridge` кэшируется через `st.cache_resource`, поэтому BGE-M3, реранкер и NLI не загружаются повторно при смене режима или перерисовке страницы. Операции сериализуются общей блокировкой доступа к embedded Qdrant и GPU. История диалога хранится в `session_state` раздельно по вкладкам и сессиям; документы размещаются в общей локальной базе. Интерфейс предназначен для доверенной локальной машины; многопользовательская авторизация отсутствует. Сбор статистики Streamlit отключён, сервер не публикуется во внешнюю сеть.

Точка входа FastAPI размещена в `api.py` (`uvicorn api:app`); `app.py` используется для Streamlit. Одновременный запуск API, CLI и Web над одним embedded-индексом не допускается. Для саммаризации в Web-режиме задаётся `RAG_LLM_API_BASE=http://127.0.0.1:8080/v1`. Streamlit, работающий в текущем терминале, завершается сочетанием Ctrl+C; затем llama-server останавливается командой `.\scripts\stop_rag.ps1 -Force`. Параметры моделей и файл `.env` хранятся локально.

Проверки и ограничения описаны в [протоколе Web-интерфейса](docs/streamlit_web.md).

## Архитектура и состав модулей

Основной маршрут обработки:

```text
PDF/DOCX/TXT/MD → BGE-M3 + Qdrant/BM25 → weighted Reciprocal Rank Fusion (RRF)
→ BGE reranker → Qwen через llama-server → mDeBERTa NLI
```

Загрузка открытого корпуса выполняется отдельным онлайн-этапом. Оценка качества использует сохранённые локальные файлы.

| Модуль | Назначение |
|---|---|
| `settings.py`, `model_runtime.py` | Типизированная конфигурация, выбор устройства и режима точности. |
| `document_parser.py` | Извлечение текста и структурных метаданных документов. |
| `document_processor.py` | Инкрементальная загрузка, сегментация и проверка дубликатов по SHA-256. |
| `hybrid_retriever.py` | Qdrant, BM25, BGE-M3, объединение результатов RRF и переранжирование. |
| `generator_verifier.py` | Генерация ответа, обработка цитат и проверка утверждений посредством NLI. |
| `pipeline.py` | Оркестрация QA-маршрута, управление ресурсами и формирование типизированного результата. |
| `summarization.py` | MMR-отбор контекста, саммаризация и фильтрация повторов и противоречий. |
| `web_bridge.py`, `app.py` | Совместное использование моделей, маршрутизация запросов и Web-интерфейс. |

| `evaluate_quality.py`, `benchmark.py`, `benchmark_ragas.py` | Корпусная оценка, измерение задержек и интеграция с оценочным инструментарием. |
| `scripts/`, `tests/`, `docs/` | Автоматизация, программные проверки и документация. |

## Окружение и LLM

Команды выполняются из корня проекта после `.\.venv\Scripts\Activate.ps1`.
Требуется установленная сборка CUDA PyTorch с поддержкой sm_120; старые сборки не поддерживают RTX 5060. Зависимости перечислены в `pyproject.toml`, offline-установка
требует локального wheelhouse. Веса расположены в `models/bge-m3`,
`models/bge-reranker-large`, `models/mdeberta-nli`, `models/llm`.

`.env` содержит настройки RAGSettings и API-токены длиной минимум 32 символа.
Он не входит в архив исходников. Основные параметры проверенного контура:

```dotenv
RAG_MODE=production
RAG_ALLOW_FALLBACK=false
RAG_MODEL_DEVICE=auto
RAG_MODEL_PRECISION=auto
RAG_DOCUMENT_ROOT=data/documents
RAG_QDRANT_PATH=data/qdrant
RAG_LLM_BACKEND=vllm
RAG_LLM_API_BASE=http://127.0.0.1:8080/v1
RAG_LLM_CONTEXT_WINDOW=4096
RAG_EMBEDDING_BATCH_SIZE=2
RAG_RERANK_BATCH_SIZE=2
```

`auto` выбирает CUDA/BF16 при поддержке; явный `cpu` сохраняется.
Production не подменяет ошибки CUDA эвристиками. Если сервер уже работает на
8080, повторно запускать его не требуется. Проверенный профиль RTX 5060 Laptop:

```powershell
.\tools\llama\llama-server.exe -m .\models\llm\Qwen2.5-14B-Instruct-Q4_K_M.gguf -ngl 35 -c 4096 -b 128 -ub 64 -np 1 --port 8080 --host 127.0.0.1
```

Конфигурация проверена на указанном стенде; её глобальная оптимальность по задержке и потреблению VRAM не установлена.

## Подготовка корпуса

Источники: [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.txt),
[PostgreSQL 16, обзор главы 27](https://www.postgresql.org/docs/16/high-availability.html),
[NIST SP 800-63B серии 800-63-3](https://pages.nist.gov/800-63-3/sp800-63b.html).
NIST — историческая редакция, заменённая 800-63-4; вопросы относятся именно к ней.
Обзор PostgreSQL не содержит детальных настроек всех подразделов главы.

```powershell
python scripts/download_quality_corpus.py --output ./data
python scripts/prepare_golden_dataset.py --corpus ./data/documents --qa-file ./data/qa_drafts.json --output ./data/golden_dataset.json
```

Исходные HTML/TXT сохраняются в `data/raw`, текст для индексации — в
`data/documents`, URL, время загрузки и SHA-256 обеих версий — в
`data/corpus_manifest.json`. Для воспроизводимости используется сохранённый снимок:
повторное скачивание может изменить хеши и потребует пересоздания набора.

`data/golden_dataset.json`: 15 QA-пар — по 3 факта, 1 синтез, 1 негатив на источник.
Каждая запись содержит `source_url`, `document_sha256`, `question`,
`ground_truth_answer`, `relevant_fragment_quote`, `is_negative`,
`created_by="ai_pregenerated"` и дополнительные ID документов/релевантных чанков.
Оболочка набора: `documents`, `corpus_root`, `examples`, версия схемы.
Подготовщик загружает QA-черновики и проверяет наличие цитат в разобранных чанках.
Разметка имеет статус `review_status=ai_draft`; до экспертной проверки набор не рассматривается как независимо валидированный Golden Dataset. Негативы требуют проверки по всему корпусу.

## Оценка качества

```powershell
python evaluate_quality.py --dataset ./data/golden_dataset.json
```

Результат: `evaluation_report.json` и Markdown-таблица в консоли. `--k 5` задаёт
срез метрик; `--output path/report.json` меняет файл. Создаётся отдельный индекс
снимка, основной `data/qdrant` не изменяется. Хеши и ссылки разметки проверяются
до запросов. Генератор не получает эталонные ответы.

- Hit@K, MRR@K, nDCG@K: метрики чанков отдельно до реранкинга (RRF) и после
  реранкинга/порога, из того же запроса. Метка документа без chunk_id означает
  релевантность всех его чанков. Негативы исключаются из этих метрик.
- Faithfulness: доля исходных утверждений, подтверждённых NLI; без утверждений
  значение `null`, а не 1. Показатель представляет собой автоматическую оценку, а не экспертное заключение.
- Answer Relevance: cosine BGE-M3 ответа и вопроса, диапазон [-1, 1]. Дополнительно
  считается cosine ответа и эталона. Показатели являются косвенными оценками семантического соответствия и не доказывают фактическую правильность; для отказов значения `null`.
- Citation Precision: доля ссылок финального ответа на релевантные и поддержанные
  NLI чанки. Recall: доля релевантных чанков, покрытых такими ссылками.
  Без ссылок precision неопределён; отказ на положительный вопрос даёт recall 0.
- Ошибки видны по каждой записи: retrieval/refusal получают 0, недоступные
  семантические метрики — `null`. Для средних указаны defined/undefined cases.

Набор из 15 QA-пар, подготовленных с использованием ИИ, предназначен для ограниченной проверки реализации. Окончательная приёмка требует независимой
экспертной разметки и более широкого корпуса положительных и негативных примеров.

## Демонстрационный интерфейс (этап 15)

```powershell
.\scripts\start_rag.ps1
.\scripts\start_rag.ps1 -Preset rfc-01 -Export .artifacts/stage15/demo.json -NoColor
.\scripts\start_rag.ps1 -IndexOnly
python demo.py --dataset holdout --list-presets
python demo.py --query "Что означает HTTP 403?" --ensure-index
.\scripts\stop_rag.ps1
```

Скрипт запуска работает относительно корня проекта, использует `.venv`, проверяет
`/health` и `/v1/models`, запускает отсутствующий сервер скрытым процессом с
профилем выше. Занятый порт не вызывает запуск дубликата. Логи и PID находятся
в `.artifacts/stage15/`. По таймауту процесс сохраняется для диагностики.
Индекс Qdrant открывается, BM25 восстанавливается; только пустой индекс вызывает
индексацию PDF/DOCX/TXT/MD из `RAG_DOCUMENT_ROOT` (`data/documents`). QA JSON и
сырые дубликаты в `data/raw` не индексируются. Частично заполненный индекс не
синхронизируется автоматически — для обновления применяется `baseline_rag.py`.

`stop_rag.ps1` проверяет PID, путь и время создания зарегистрированного скриптом запуска
процесса и запрашивает закрытие окна. Для скрытого консольного сервера применяется команда `./scripts/stop_rag.ps1 -Force`: после проверки идентичности процесс завершается
принудительно с ожиданием выхода. Процессы, не зарегистрированные скриптом запуска,
скрипт не останавливает. Индексы сохраняются.

Для холодного старта с автоматическим откатом:

```powershell
.\scripts\test_cold_start.ps1
```

Требуется существующий рабочий индекс внутри проекта. Обёртка останавливает
зарегистрированный скриптом запуска сервер, проверяет свободный порт, сохраняет SHA-256,
перемещает весь каталог Qdrant/BM25 в уникальную `.backup_indexes/`, запускает
`rfc-01` и восстанавливает оригинал в `finally`. Тестовая база удаляется только
после совпадения хешей восстановленного оригинала. При ошибке восстановления
копии сохраняются; пути указаны в `.artifacts/cold-start/<run>/recovery.json`.
Одновременный запуск другого процесса, использующего рабочий индекс, не допускается.
Если порт занят незарегистрированным сервером, тест прерывается без переноса базы.

В интерактивном режиме доступны номер вопроса, `/preset ID`, `/list`, `/quit`
или произвольный вопрос. Эталонные ответы не передаются генератору. Четыре панели
после выполнения запроса показывают Top-5 с RRF/реранкером, черновик и итог,
решение NLI и вероятности классов, времена стадий. `UNVERIFIED` — решение
фильтра; оно не обязательно означает класс `NEUTRAL`. Черновик явно помечен
как неподтверждённый. Чанки читаются из трассы того же запроса без повторного поиска.

`--export path.json` сохраняет полный JSON и автономный HTML рядом с ним.
В интерактивном режиме файлы перезаписываются последним успешным запросом.
Экспорт содержит вопросы, тексты документов и черновой ответ; передача файлов требует учёта содержащихся в них данных. Результат экспорта отражает выполнение демонстрационного запроса и не является новым отчётом оценки качества.

## Пользовательские документы: инкрементальная загрузка

Команды выполняются из корня проекта в активированном окружении `.venv`:

```powershell
python scripts/manage_index.py --add "C:\Documents\manual.pdf"
python scripts/manage_index.py --scan "C:\Documents\new-files"
python scripts/manage_index.py --status
```

Обработка DOCX выполняется через `python-docx==1.2.0` с сохранением порядка абзацев, заголовков и таблиц. Применяются общий механизм чанкинга и SHA-256-дедупликация. Поддержка Word включена в группы зависимостей `documents` и `web`. Устаревший бинарный формат `.doc` не поддерживается.

TXT/MD читаются как UTF-8 (BOM поддерживается), текстовые PDF — через существующий
локальный PyMuPDF. Пакет входит в optional dependency `documents`; веса BGE-M3
и реранкера должны быть подготовлены локально. OCR для сканов не выполняется.

Загрузчик делает временный снимок файла и вычисляет SHA-256 до парсинга. Уже
завершённый хеш пропускается, в том числе у файла с другим именем и у документов
прежнего корпуса. Изменившееся содержимое считается новой версией: старые версии
не удаляются автоматически. Пути источников сохраняются для цитирования;
пользовательские исходники не копируются в `data/documents` навсегда.

Новый профиль не меняет старые чанки: цель 650, максимум 800 токенов локального
BGE-токенизатора, overlap до 75 токенов из целых предложений, без переноса между
разделами. Короткие разделы дают короткие чанки. Overlap может быть меньше 50,
если целое предложение не помещается в 75 токенов. Слишком длинное предложение,
строка таблицы или метаданные вызывают явную ошибку; текст не обрезается.
Пунктуационный разделитель предложений консервативный, не полноценная NLP-модель.

Параметры инкрементального маршрута задаются отдельно; существующий профиль поиска сохраняется:

```dotenv
RAG_INGESTION_TARGET_TOKENS=650
RAG_INGESTION_MAX_TOKENS=800
RAG_INGESTION_OVERLAP_TOKENS=75
RAG_INGESTION_BATCH_SIZE=2
RAG_INGESTION_MAX_CHUNKS=10000
```

Qdrant пополняется пакетами не более двух чанков; BGE-M3 использует существующий
`torch.inference_mode()`. Векторы старых документов не пересчитываются. BM25Okapi
не имеет append API: его разреженная статистика пересобирается один раз после
нового документа и атомарно сохраняется. Токены всего корпуса остаются в RAM.
Эта защита ограничивает рабочий пакет VRAM, но не гарантирует отсутствие OOM
при занятой другими приложениями карте.

Каждый чанк содержит SHA-256, ожидаемое число чанков и порядковый номер. После
аварийного завершения неполный документ исключается из dense/BM25-поиска.
Повторная загрузка того же файла удаляет только его неполные записи и выполняет
индексацию заново; остальные документы сохраняются. Сбой записи закрывает клиент
для дальнейших операций — требуется повторный запуск команды. Ошибки парсинга отдельных файлов
при `--scan` выводятся в JSON, остальные файлы обрабатываются; код возврата 1
означает хотя бы одну ошибку. Успех/дубликат/пустое сканирование дают код 0.

`--status` загружает только payload из Qdrant: `documents` и `chunks` считаются
для завершённых документов; `incomplete_documents` показывает незавершённые,
`stored_chunks` — все физически записанные чанки. Модели не загружаются.

Embedded Qdrant допускает один процесс-владелец каталога. Перед запуском команды необходимо завершить CLI или сервис, удерживающий индекс. Для добавления внутри уже открытого процесса применяется `DocumentProcessor(settings).add(path, pipeline.retriever)`
с последовательным доступом. Одновременная независимая запись не поддерживается.

Проверки загрузчика: [протокол](docs/ingestion_pipeline.md).

## Саммаризация документа

Независимый `SummarizationPipeline` запускается через `baseline_rag.py`:

```powershell
.\scripts\start_rag.ps1 -IndexOnly
$docId = (Get-FileHash -LiteralPath data/documents/rfc9110.txt -Algorithm SHA256).Hash.ToLower()
python baseline_rag.py --summarize $docId
python baseline_rag.py --summarize $docId --json > summary.json
```

Файл должен быть уже проиндексирован; `doc_id` — SHA-256 именно той версии файла,
которая находится в базе. Новые файлы предварительно индексируются через `manage_index.py`.
`--summarize` не совмещается с `--query`, `--index`, `--interactive`, `--benchmark`.
QA-маршрут, его реранкинг и строгая проверка цитат не изменены.

Из документа выбирается до 30 равномерно расположенных содержательных чанков.
BGE-M3 оценивает их близость к центроиду; MMR отбирает до 12 разнообразных чанков.
Если уникальных фрагментов меньше, повторы ради заполнения лимита не добавляются.
Длинный контекст обрабатывается группами map/reduce с проверкой токенов и лимитом
вызовов; выбранные фрагменты не отбрасываются просто из-за окна 4096 токенов.

Специальный промпт требует 2–3 абзаца, список критических данных и ссылки `[Si]`.
Промежуточные и итоговые предложения проверяются по исходным фрагментам:
удаляются при `P(contradiction) > 0.3`, затем при cosine similarity `> 0.85`
к уже принятым предложениям. `neutral` допускается только здесь. Неудачная
оценка NLI, переполнение контекста или усечённая генерация дают явную ошибку.

Настройки: `RAG_SUMMARY_POOL_SIZE=30`, `RAG_SUMMARY_TOP_K=12`,
`RAG_SUMMARY_MMR_LAMBDA=0.6`, `RAG_SUMMARY_CONTRADICTION_THRESHOLD=0.3`,
`RAG_SUMMARY_SIMILARITY_THRESHOLD=0.85`, `RAG_SUMMARY_OUTPUT_TOKENS=768`,
`RAG_SUMMARY_MAX_GENERATION_CALLS=16`.

JSON содержит исходную и очищенную выжимку, выбранные источники, все решения
фильтров с вероятностями NLI и посылками, число генераций и время этапов.
После фильтрации текст может содержать меньше абзацев или пунктов списка.
Саммаризация характеризует выбранные фрагменты и не гарантирует охвата всего документа: критические числа
могут оказаться вне выбранных чанков. `neutral` не подтверждает факт; NLI может
пропустить искажение, а cosine — удалить близкие, но различные факты. Абсолютная
полнота, достоверность и отсутствие смысловых повторов не гарантируются.

Проверки режима: [протокол](docs/summarization.md).
