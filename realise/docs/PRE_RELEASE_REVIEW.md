## Дополнительные границы релиза

Ведущий обнаружил в `app.py` незадействованную проверку API-токенов из settings
и отсутствие FastAPI lifespan для close. Это не исправлено косметическим
рефакторингом: HTTP-сервис нельзя объявлять защищённым многопользовательским
production API. Текущая демонстрация — локальный CLI; перед сетевой публикацией
необходим отдельный аудит аутентификации, лимитов запросов и lifecycle API.
Динамическая проверка TestClient заблокирована отсутствующей зависимостью FastAPI
в текущей .venv (ModuleNotFoundError); отсутствие auth/lifespan подтверждено
статически, HTTP endpoint в этом аудите не объявляется протестированным.

Проверки ниже оценивают сохранение поведения на коротком контроле, а не доказывают
сохранение Hit@5 на всём holdout. Исторические 100% Hit@5 не пересчитываются.

### Подтверждённые проблемы

1. Критично — у `GeneratorVerifier` нет закрытия, хотя пайплайн это ожидает  
- **Файл/строки**: [generator_verifier.py](/C:/Hakatons/RT/generator_verifier.py):887-920, [pipeline.py](/C:/Hakatons/RT/pipeline.py):373-399  
- **Триггер**: создать `RAGPipeline(..., verifier=GeneratorVerifier(...))` и вызвать `pipeline.close()` (или `with`-контекст завершится).  
- **Последствие**: `Pipeline.close()` вызывает `component.close()` для `_legacy_verifier`; у класса это метода нет → ошибка добавляется в `errors`, закрытие заканчивается `PipelineError`, возможен неполный cleanup (особенно для LLM-ресурсов).  
- **Минимальный патч**: добавить `close()` в `GeneratorVerifier`, закрывающий `generator` и `verifier` при наличии `close`, с идемпотентностью.  
- **Проверка**: в тесте создания/закрытия пайплайна с legacy-верификатором убедиться, что `pipeline.close()` отрабатывает без исключения и повторные входы/выходы из `with` не накапливают ошибки.

2. Средне — `HybridRetriever.close()` не закрывает/не освобождает нейросетевые модели, только Qdrant  
- **Файл/строки**: [hybrid_retriever.py](/C:/Hakatons/RT/hybrid_retriever.py):738-744, 117-149, 167-197  
- **Триггер**: создать `HybridRetriever` с реальными моделями, вызвать `close()`, затем заново инициализировать Retriever в том же процессе (8GB VRAM, локальные модели).  
- **Последствие**: в close освобождается только embedded-Qdrant, а владение `SentenceTransformerEncoder._model` и `CrossEncoderReranker._model` не завершается явно; на длительном runtime может проявляться рост/флэттенинг памяти после циклов recreate.  
- **Минимальный патч**:  
  - добавить `close()` в `SentenceTransformerEncoder` и `CrossEncoderReranker` (перенос `self._model` на CPU, `del`, безопасный `torch.cuda.empty_cache()` под `torch.cuda.is_available()`)  
  - в `HybridRetriever.close()` вызывать эти `close()` у `encoder/reranker` до/после `QdrantClient.close()`  
- **Проверка**: до и после `close()` замерять `torch.cuda.memory_allocated()`/`memory_reserved()` по циклу `init -> close -> gc.collect() -> init`.

3. Низко-среднее — лишние повторные CPU→GPU перенесения в батче reranker  
- **Файл/строки**: [hybrid_retriever.py](/C:/Hakatons/RT/hybrid_retriever.py):217-233  
- **Триггер**: кандидатные тексты с overflow‑окнами в `self._tokenizer(... return_overflowing_tokens=True ...)` (длинные тексты, много окон).  
- **Последствие**: в каждом внутреннем цикле `start` тензоры каждого окна копируются на GPU заново (`.to(self._device)`), создавая лишний transfer overhead и jitter латентности.  
- **Минимальный патч**: перенести токенизованные тензоры на `self._device` один раз перед внутренним циклом (кроме `overflow_to_sample_mapping`), затем нарезать уже на GPU.  
- **Проверка**: A/B на одной и той же выборке: время rerank + профилирование HtoD transfer (`torch.cuda` + `nvidia-smi`), без изменения batch без измерений.

## Подтверждённые находки

1. **[Критично] N+1 запросов к llama-server только для оценки токенов перед генерацией**
- **file:line:** `generator_verifier.py:361-374`, `546-566`
- **Воспроизводимый триггер:** `llm_api_base` включён (llama-server), `llm_tokenizer_mode == "llama_server"`, вопрос с несколькими релевантными чанками (например, top_k>=10).
- **Последствия:** перед самим `chat/completions` делается `1 + len(contexts)` HTTP POST к `../tokenize` + JSON сериализация каждого варианта контекста, что даёт линейный сетевой overhead до генерации. На холодном запуске и при медленном loopback это сильно бьёт по `TTFT` и `generation_ms`.
- **Минимальный патч (без ломки mypy):** убрать дорогой пересчёт токенов “с нуля” для каждого кандидата:
  - кэшировать стоимость immutable-части (`system_prompt` + префикс запроса/ревизии),
  - считать token-delta только для добавляемого источника (или кешировать `json` каждого `SourceContext`),
  - в `generate()` поддерживать running budget инкрементально.
  Типы: `dict[str, int]` для кэша, локально в методе, чтобы сохранить strict.
- **Проверка:** добавить счётчик вызовов `count_tokens`; для фиксированного `top_k` до патча он ≈ `O(n)`, после — не должен расти линейно по размерам контекста (кроме первого прогона новых source payload).

2. **[Высокая] Квантовая упаковка источников делает квадратичную работу сериализации**
- **file:line:** `generator_verifier.py:534-566`
- **Воспроизводимый триггер:** тот же сценарий: много source-кандидатов, большой общий размер чанков.
- **Последствия:** `candidate = {**selected, key: value}` и `json.dumps(...)` пересобирают всю карту источников на каждом шаге, из-за чего CPU/memory растут быстрее, чем линейно; это отдельный источник jitter на стороне API-цикла до обращения к модели.
- **Минимальный патч:** заменить копирование dict на мутабельное добавление одного источника и переиспользовать подготовленные JSON/токеновые префиксы.  
  Примерно:
  - хранить `selected: dict[str, SourceContext]` и не создавать новый dict каждый шаг;
  - использовать `json.dumps(..., separators=(",", ":"), ensure_ascii=False)` один раз для новых кусков, а не для всего growing-пакета.
- **Проверка:** локальный профайлинг `python -X importtime`/`cProfile` на одной и той же выдаче: время сериализации должно перестать расти сверхлинейно при росте `top_k`.

3. **[Средняя] Избыточная глобальная блокировка в `query()` сериализует весь запрос целиком**
- **file:line:** `pipeline.py:225-372`
- **Воспроизводимый триггер:** 2+ одновременных `/query` к одному `RAGPipeline`-экземпляру.
- **Последствия:** даже независимые этапы (внешний retrieval, верификация, формирование ответа) выполняются строго по одному; это искусственно уменьшает пропускную способность и маскирует настоящую нагрузку GPU/IO.
- **Минимальный патч:** разделить критические секции:
  - под блокировкой: `_ready()`, lazy-init и присваивание ссылок на компоненты;
  - вне блокировки: `search_trace`, `generate`, `verify`, упаковка `response`.
  - оставить синхронизацию внутри самих компонентов (`LocalLLMGenerator`, `NLIFactVerifier`) для состояния.
- **Проверка:** параллельный прогон 4–8 запросов: без этого изменения p95 растёт почти линейно с количеством одновременных, после — улучшение на CPU-bound нагрузке при сохранении корректности.

4. **[Средняя] `GET /health` может вызывать lazy-init ретривера**
- **file:line:** `app.py:40-42`
- **Воспроизводимый триггер:** вызов `/health` в новом процессе до первого query.
- **Последствия:** health-check инициирует потенциально тяжёлую инициализацию `retriever` (I/O к индексу/хранилищу), что повышает jitter и может исказить мониторинговые метрики warm-up.
- **Минимальный патч:** в health возвращать `chunks=0`, если `rag._retriever is None`; обращаться к `rag.retriever` только если компонент уже создан.

5. **[Низкая] TTFT собирается только в stream-пути**
- **file:line:** `generator_verifier.py:419-472`, `pipeline.py:310`
- **Воспроизводимый триггер:** `llm_api_stream=False` (или конфиг по умолчанию не обеспечивает stream).
- **Последствия:** нет `llm_ttft_ms`, сложно отделить queue wait/TCP-пик сервера от чистой генерации; при llm-server + 8GB VRAM и переменной конкуренции это усложняет инцидент-диагностику.
- **Минимальный патч:** в проде явно включить потоковый режим хотя бы для мониторинга/профиля и фиксировать `ttft_ms`; либо добавить отдельный “metrics mode”, где stream используется только для метрик, а ответ собирается как и сейчас.
- **Проверка:** в нагрузочном тесте после включения режима проверить, что `llm_ttft_ms` стабильно присутствует и коррелирует с очередью/нагрузкой.

### review_edge_cases

Ниже только подтверждённые точки отказа из приведённого снимка.

1. **[high] Деление на ноль в смешивании RRF с весами `dense_weight`/`sparse_weight = 0`**
- `hybrid_retriever.py:684-689`
- Триггер: `RAGSettings(dense_weight=0, sparse_weight=0)` с любым непустым поиском.
- Последствие: `ZeroDivisionError` в `search()` (формула `fused/( (dense_weight+sparse_weight)/(rrf_k+1) )`), падает весь запрос.
- Минимальный патч:
  - До деления посчитать `total_weight = dense_weight + sparse_weight`.
  - Если `total_weight <= 0`, выбрасывать `ValueError("At least one retrieval weight must be > 0")`.
- Проверка:
  - Запустить query при `dense_weight=0, sparse_weight=0` и подтвердить контролируемую `ValueError`, а не `ZeroDivisionError`.

2. **[high] Неконечные/невалидные скоры из Qdrant не валидируются до ранжирования/возврата**
- `hybrid_retriever.py:623-629` и косвенно `pipeline.py:332-339` → `SourceCitation.score`.
- Триггер: индекс возвращает `hit.score = inf | -inf | nan`.
- Последствие: невалидные значения проходят в ранжирование и затем в валидацию ответа (`allow_inf_nan=False`), что приводит к неожиданному падению на другой стадии.
- Минимальный патч:
  - В `search()` валидировать `hit.score` через `math.isfinite()` перед использованием.
  - Инициировать `RetrievalError` с явной диагностикой источника индекса.
- Проверка:
  - Подменить слой Qdrant-ответа с `inf` скором и проверить, что падает с `RetrievalError("Non-finite dense score")`.

3. **[high] Malformed HTTP в `_HTTPBackend`: JSON парсинг не полностью защищён**
- `_HTTPBackend.count_tokens`: `generator_verifier.py:369-373`
- `_HTTPBackend.complete`: `generator_verifier.py:403-417`
- `_HTTPBackend._stream`: `generator_verifier.py:449-451` и `426-473`
- Триггер: сервер отвечает не JSON/битый SSE-пакет (`data: {...`), HTML при ошибке и т.д.
- Последствие: неожиданные `JSONDecodeError`/другие исключения вне текущего контекста, нестабильная типизация ошибок, сложнее triage.
- Минимальный патч:
  - Обернуть `response.json()` и `json.loads(data)` в `try/except json.JSONDecodeError`.
  - На ошибке поднимать `VerificationError("Malformed ... response")`, не меняя сигнатуру результата.
- Проверка:
  - Протестировать с fake-эндпоинтом, возвращающим `text/html` и битые `data:`-кадры в стриме; ожидать строгое `VerificationError`.

4. **[medium] Поведение “20k-ввода” частично реализовано, но в API-слое нет верхней границы запроса**
- `app.py:30-33` (`QueryRequest.query` только min_length), `pipeline.py:215-219` (порог в settings 4000 по умолчанию).
- Триггер: `POST /query` с очень длинным запросом при `max_question_chars` конфигурационно повышенном до 20k/32k.
- Последствие: лишняя нагрузка на ретривер/LLM до остановки на более глубоком уровне (и разный путь ошибок).
- Минимальный патч:
  - Добавить предвалидацию в API: лимит `query` в `QueryRequest` или в роуте через `rag.settings.max_question_chars`.
- Проверка:
  - Запрос 20k символов с лимитом из конфига -> быстрый HTTP 422 с понятным `detail` до входа в поиск.

5. **[info] Проверка “пустой/спецсимволы ввод” по сути уже есть, но не на уровне FastAPI**
- Пустой ввод: `app.py:31` (min_length=1) + `pipeline.py:217`.
- Инъекционные символы/контрольные символы: `pipeline.py:219-220` блокирует `Cc/Cf` (кроме `\n\t\r`).
- Последствие: поведение в целом закрыто, но диагностика в API приходит уже после части пайплайна.
- Риск остаётся в качестве “дальнего” этапа ошибок, не блокера.
- Минимальный патч (если нужна ранняя и однородная диагностика): поднять те же правила в валидацию запроса API.
- Проверка:
  - `""`, `\x00`, `\u200f`, 20k обычной строки — confirm consistent/clear 422 or ValueError path.

### review_architecture

Ниже — только подтверждённые находки по вашему срезу.

1. **[HIGH] Неполный lifecycle при ошибке `close()` у компонентов пайплайна**  
   - **Файл:строка**: [pipeline.py](pipeline.py):375–399  
   - **Триггер**: один из `component.close()` выбрасывает исключение (например, временно недоступный ресурс или кастомный мок-компонент в тестах).  
   - **Последствие**: `_closed` выставляется в `True` до завершения очистки, после чего повторный `close()` не выполняет повторную попытку, а некоторые ресурсы могут остаться неосвобождёнными (риск утечки при перезапусках внутри процесса).  
   - **Минимальный патч**: устанавливать закрытие “флагом” только после прохода по компонентам; при ошибке оставлять объект в режиме “attempted close” или `closing`, чтобы повторный close мог добирать оставшиеся ресурсы.  
   - **Проверка**: добавить тест с компонентом, который отрабатывает `close()` с ошибкой, и проверить, что после неуспешного закрытия повторный `close()` пытается закрыть оставшиеся компоненты и не “залипает” в закрытом состоянии до успешного освобождения.

2. **[HIGH] `GET /health` инициирует создание Retriever’а**  
   - **Файл:строка**: [app.py](app.py):40–42  
   - **Триггер**: холодный старт сервиса и первый запрос `/health`.  
   - **Последствие**: из-за доступа `rag.retriever` триггерится ленивое создание retriever-а (возможна инициализация тяжелых зависимостей и потребление RAM/VRAM вне запроса обработки/индексации).  
   - **Минимальный патч**: читать размер чанков напрямую из внутреннего поля без перехода в property, например:
     `chunks = rag._retriever.size if rag._retriever is not None else 0` (или отдельный безопасный метод `maybe_retriever_size()`).  
   - **Проверка**: на холодном старте вызвать `/health` и убедиться, что не происходит инициализация encoder/llm/токенизатора.

3. **[MEDIUM] Дублирование токенизации в отборе контекста запроса**  
   - **Файл:строка**: [generator_verifier.py](generator_verifier.py):548–564, 312–313, 361–374  
   - **Триггер**: `query()` с большим `top_k` / длинными chunk-ами; для каждого кандидата повторно считается токенизация всего текущего префикса + кандидат.  
   - **Последствие**: O(n²) рост работы; в режиме llama-server с `llama_server` токенизация может идти через HTTP на каждом шаге (`count_tokens`), повышая latency и нагрузку на локальный сервер.  
   - **Минимальный патч**: кэшировать `count_tokens` внутри одного запроса (по сериализованному блоку источника), и считать базовый бюджет один раз; затем инкрементально добавлять только новый источник.  
   - **Проверка**: профилировать число вызовов `count_tokens` и p95 latency для фиксированного набора документов до/после; сравнить отсутствие изменений в покрытии выбранных источников.

4. **[MEDIUM] Жёстко зашитый шаблонный оверхед контекста (128)**  
   - **Файл:строка**: [settings.py](settings.py):260 и [generator_verifier.py](generator_verifier.py):546  
   - **Триггер**: модели/шаблоны с отличающимся системным overhead (особенно при llama-server).  
   - **Последствие**: false-negative на `context_budget` при “ровных” лимитах, излишняя отбраковка источников или некорректный отказ `context_budget_exceeded`.  
   - **Минимальный патч**: вынести в конфиг, напр. `llm_template_overhead_tokens` (по умолчанию 128), использовать в обеих валидациях (`settings` и генераторе).  
   - **Проверка**: для краевого случая с коротким окном контекста показать, что при увеличении/уменьшении оверхеда меняется только поведение лимита, а не качество выдачи.

5. **[MEDIUM] Нет явного освобождения NLI-модели и связанных ресурсов**  
   - **Файл:строка**: [generator_verifier.py](generator_verifier.py):651–676 и 873–878  
   - **Триггер**: циклическое создание/закрытие `NLIFactVerifier(backend=TransformersNLI)` в долговременном процессе (8GB VRAM, offline).  
   - **Последствие**: `del self.backend` в `NLIFactVerifier.close()` не гарантирует детерминированное освобождение CUDA/CPU памяти, возможен рост потребления памяти и последующий OOM.  
   - **Минимальный патч**: добавить `close()` в `TransformersNLI` (`del model/tokenizer`, `torch.cuda.empty_cache()` при CUDA) и вызывать его из `NLIFactVerifier.close()`.  
   - **Проверка**: прогнать цикл open/close 10–20 раз и наблюдать, что VRAM стабилизируется, а не монотонно растёт.

6. **[LOW-MEDIUM] `GeneratorVerifier.close()` может не закрыть verifier при ошибке закрытия generator’а**  
   - **Файл:строка**: [generator_verifier.py](generator_verifier.py):917–920  
   - **Триггер**: `self.generator.close()` выбрасывает исключение.  
   - **Последствие**: `self.verifier.close()` не выполняется, возможна утечка/зависание состояния NLI при смешанных пайплайнах.  
   - **Минимальный патч**: закрытие через `try/finally` или агрегацию ошибок (как у `RAGPipeline.close()`), чтобы оба компонента пытались закрыться.  
   - **Проверка**: тест с фейковым генератором, который падает в `close()`, и проверка факта вызова `close()` в verifier.
